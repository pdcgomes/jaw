# Jaw for the Mac

The Mac's interface on jawd's socket, as [the Mac design](../docs/plans/2026-10-26-jaw-mac-design.md) has it and in [the Mac plan](../docs/plans/2026-10-26-jaw-mac-plan.md)'s order. This is Mac-M1, text every day, under way.

## Building

The tools sit behind mise (`mise.toml` here pins Tuist, SwiftFormat and SwiftLint). Builds and tests run on the build Mac, `build-mac` in `~/.ssh/config`, so this Mac stays free; when it doesn't answer they run here.

```sh
cargo build -p jawd --bin jawd              # the jawd the live tests and --demo run, built here
mac/scripts/build-mac test JawKit           # the client: fixtures, window models, a fake jawd, a real one
mac/scripts/build-mac test JawThemes
mac/scripts/build-mac test JawUITests       # the layout, and its reference pictures in both looks
mac/scripts/build-mac test JawHarnessTests  # the harness: its catalog, flags, pictures and scenes
mac/scripts/build-mac build jaw
mac/scripts/build-mac release <folder>      # Jaw.app in Release, as the measurements take it, back here
make mac                                    # Jaw.app with jawd, jaw-engine and jaw inside, signed
make mac-test                               # the four suites above
```

The build Mac has no Rust or Go, so jawd, jaw and jaw-engine are built here and their binaries go with the checkout. `mise exec -- tuist generate --no-open` makes `Jaw.xcworkspace` for Xcode.

A debug build never opens the owner's jaw folder: without `--home` or `JAW_HOME` it runs `jawd --engine demo`, a made-up account, in a folder of its own, and stops it on quitting. Only a signed release registers its jawd at login (Jaw › jawd at Login…), under the label `jaw agent install` uses, offering to take over the terminal's agent on a click and keeping a jawd newer than its own.

The app's options: `--demo`, `--home <folder>`, `--bench launch|open|memory|idle|pictures|library`, which prints one JSON line and quits, `--downloads <folder>`, where Save puts files in place of Downloads, so a run trying it leaves nothing in yours, a folder there is (a relative one from where the app starts), or the app won't start, and `--snapshot <png>`, which draws the window once the chat list has stopped changing and a chat is open (or the sheet over it); `build-mac snapshot` runs it on a demo folder of its own each time, removed after. With `--snapshot`, `--keys` presses shortcuts through the app's own event handling half a second apart and prints the panes after each, with the palette's selected answer, the pane's selected message and each library pane's kind, items, selection and whether it has the keys (a key with ⌘ is offered to the window's views first, as AppKit offers it to a key window's, since the build Mac runs the app inactive): `cmd+shift+d`, `ctrl+cmd+right`, `cmd+opt+e`, `tab`, a digit or a letter, `space`, and the steps `size:1200x800`, `save:<layout>`, `revert`, `settings`, `terminal-panes` (Open the Terminal's Panes), `drop:<row>:<middle|left|right|top|bottom>`, `promise`, which keeps the selected message's file's drag promise as a drop on the `--downloads` folder would, since nothing drives a pointer, `window`, which gives the main window the keys again, as a click on it would while a panel such as Quick Look's has them, and `menu:list:<row>`, `menu:header`, `menu:message:<row>` and `menu:bar:<menu>`, which print in place of the panes the items of a chat's menu in the list, the focused pane's menu, the menu of a row of the focused pane's transcript (a system or call line there gives the pane's menu), or one of the menu bar's menus as it opens, greyed ones in brackets; `vote:<option>`, which votes in the focused pane's newest poll as a click on that option does and prints the poll as jawd's row then has it; `poll:<question>|<option>|<option>`, with `|several` at its end to allow several answers, which sends a poll to the focused pane's chat as the poll form's Send does and prints its newest poll; and `poll-form`, with the same after a colon to fill it in, which opens the poll form, so the picture is the sheet, each line then saying the form's question, its options by their numbers and what the field being edited holds; `menu-key:<key>`, before a step that pops a menu up, which presses `<key>` in that menu once it's open, as the keyboard would (a digit, `t`, `p`, `r`, `down`, `up`, `return` or `escape`, or several joined by dots, as `menu-key:down.return`), Esc a second after if it's still open, and says the menu's items, whether Esc had to close it and the focused pane's newest poll after; and `click:<x>:<y>`, a click at that point of the key window (the poll form's sheet, or else the main window, when the app isn't active, as it isn't when the build Mac runs it), in points from its top left. While Quick Look shows something, the line says what, with each clone's mode and quarantine. Rows count from 0. For example, `mac/scripts/build-mac snapshot /tmp/x.png --keys "cmd+d,save:Work,cmd+w,ctrl+cmd+1"`.

## Component harness

Jaw Harness (`JawHarness`) draws the app's components and screens from made-up rows and the protocol's fixtures, in each theme, look and density, and asks jawd for nothing, as [the harness's design](../docs/plans/2026-10-27-jaw-mac-harness-design.md) has it. Its scenes are listed by section on the left, with the conditions they're drawn in under them; each says what to look at, and each band of specimens what would be wrong with it. The Screens section draws the whole window from a `Screen`, which gives jawd's situation, the chats, the chats open, the layout's name, focus mode and the size, as the app draws it from jawd's windows, through the same `WindowContent`.

```sh
mac/scripts/build-mac harness [scene] [options]    # built on the build Mac and opened here
mac/scripts/build-mac shot <scene> <png> [options] # one scene drawn into a picture
mac/scripts/build-mac sweep                        # every scene in each variant, into mac/build/review
```

After a sweep, the review canvas, `.atelier/mac-harness.canvas.tsx`, shows each scene's pictures by section (`atelier open .atelier/mac-harness.canvas.tsx`). Mark each one Right, or Needs work with a note; the marks are kept under `marks`, by scene, with the hashes of the pictures they were made on, and a scene whose pictures change after its mark asks again. Agents read the marks with `mac/scripts/review-marks`, a line a scene (`--json` for the same as JSON), by the canvas's rule: a mark counts only while its hashes are that scene's pictures' hashes in the sweep's `manifest.json`, in order, so a scene whose pictures have changed since is changed since marked, and one with no mark, or a cleared one, hasn't been looked at. The canvas's pictures come from `build-mac sweep`, which writes them and the canvas's data, with their hashes, together: a `--sweep` run by hand into `mac/build/review` would leave new pictures under the last sweep's hashes until `mac/scripts/review-data` writes the data again.

Its options: `--scene <id>`, `--theme <id>`, `--appearance dark|light`, `--look bubbles|lines`, `--density comfortable|compact`, `--text-size <11…17>`, `--font system|mono`, `--reduce-motion`, `--window <width>x<height>`, `--stage-only`, `--snapshot <png>` and `--sweep <folder>`.

To add a component, write a scene in `JawHarness/Sources/Scenes/` and register it in `BuiltInScenes.swift`. `scripts/check-harness`, which every build runs, fails if the harness names `Jawd`, or JawKit's `Client`, which opens jawd's socket itself, or if the app target defines a view or a view controller of its own, which belongs in `JawUI`, where the harness can draw it from values.

## How the interface is put together

- **Components** (`JawUI/Sources/Components`): the type scale (`TextStyle`), spacing, radii, lines and motion (`Space`, `Radius`, `Stroke`, `Motion`, which stops under Reduce Motion), colours by `Tone` from the theme's roles, and the controls every surface uses (`IconButton`, `Labels`, `Surface`, and `.textStyle`, `.tone`, `.card`, `.panel` and `KeyCap` in SwiftUI). `scripts/check-components`, run by every build, fails on a font, a radius or a line width set by hand anywhere else; the messages' own fonts are the layout's.
- **Commands** (`JawUI/Sources/Commands`, the app's in `JawApp/Sources/Commands.swift`): each thing the app does is written once, with its menu title, its phrase for the palette, its key and its menu. The menu bar, the toolbar's menus, the panes' context menus, the palette and the keys sheet are made from that list, so every key shows in a menu and every menu item says its key. `Shortcut` gives menus a Shift letter's capital. Debug builds stop at launch on two commands with one key.
- **Panes and layouts** ([the grid layouts design](../docs/plans/2026-10-26-jaw-mac-grid-layouts-design.md)): `PaneGrid` is the layout as slots on a grid's lines, with its rules tested on their own; `GridView` sets the panes' frames by hand, so they follow a live resize in the same frame; `LayoutBook` keeps the named layouts and an edited shape apart from the saved one; `LayoutEditorModel` and its sheet are the editor. One box, the window's (`BoxPlace`), shows the focused chat's composer. Open the Terminal's Panes (the Layouts menu and the palette) reads the panes jawd keeps for the terminal, `layout.get` for `jaw`, as a grid in place of the unsaved panes (`TerminalPanes`). A pane whose chat the chat list doesn't hold, in any layout, gets its row from jawd through a window of one row around the chat, in `all` and then `archived`, one at a time and the focused slot's first (`Jawd.lookUp`), and a slot whose chat won't have a pane says why, that it's gone or jawd's words for refusing the lookup, from words the window's panes carry (`WindowContent.Panes.unopened`).
- **Pictures** (`JawUI/Sources/Pictures`): the layout lays each picture out as a slot, its place from the row's `w` and `h` before any pixel, so a preview landing moves nothing. `MessagePictures` picks the preview its pixels need (jawd's 256 for 256 pixels or fewer, the 768 above, never the file, or a link's thumbnail, a JPEG alone), decodes it on the image queue, four at a time, at exactly the pixels drawn, keeps it in a cache of 64 MB drawn least recently first out, emptied while the window is closed, and stands the blurred thumbnail in meanwhile; a cell asks for its slots as it's given a row and lets them go when it's reused or its row leaves the transcript, so a fling decodes what it stops on; a preview, or a thumbnail over the well, fades in on Core Animation. Each download state is drawn over its picture or on its card, with what can be done about it.
- **Files** (`JawUI/Sources/Files`): `MediaOffer` says what a message's file, or an album item's, offers in each state, which the click, the keys (Space, Enter, ⌘↩, s), the message's menu and the Message menu share. What's looked at with Quick Look, opened, opened with another app or dragged out is a clone of jawd's file in the app's own temporary folder (`Opened`), named as `media.save` names a copy, so an app that edits what it opens never changes jawd's file, which every message with it shares; each is quarantined as a message's attachment, so macOS checks what someone sent before it runs, and one looked at or opened is read-only, so an app that edits it offers to duplicate it; each run keeps its clones in a folder of its own, emptied as it quits, and one starting empties those of runs that have gone; a file not here drags out as a promise kept in the app, `media.save` writing it into the app's own folder and the app putting it where it's dropped, quarantined, under its name or with a number when that's taken, and one looked at or opened before it's here is asked for and opened once it is. A copy saved into Downloads (Save, Save HD Copy, Show in Finder) is the one jawd's `media.save` writes, which the app quarantines the same way once jawd answers, until jawd does it itself (the Mac design's P13).
- **Links and polls** ([their plan](../docs/plans/2026-10-30-jaw-mac-links-and-polls-plan.md)): a link's card sits under its text, its height known from the row, so a thumbnail read late moves nothing; its thumbnail is a picture slot over its well and link symbol, filled by the image queue from jawd's folder as a photo's preview is (Pictures, above), a JPEG alone. A poll's options are regions a click votes in (`Voting.choosing`), as are its message's Vote menu and Enter on a selected poll; the + menu's Poll… opens the poll form (`PollForm`), and a poll jawd turns down opens it again as it was. The palette lists `find`'s links, ⌘G going to a link's message as to a message's.
- **The library** (`JawUI/Sources/Library`, [its plan](../docs/plans/2026-11-01-jaw-mac-library-plan.md)): a pane like a chat's, ⌘L for every chat and a chat's header's button, or ⌥⌘L, for that chat, beside the focused pane (`LibraryPane`); its slot's chat is `library` or `library:` and the chat's ID, kept with the layouts and never looked up as a chat. `LibraryLayout` lays a `library.watch` window's items out at the pane's width before any picture: a kind's newest first under their months, photos and videos as tiles of 96 to 128 points, each taking jawd's 256 preview through the picture slots and the cache every pane shares, voice messages, files and links as rows, and every kind's window as a shelf of each; an `NSCollectionView` with prefetching places them, and a kind's window moves around the item at the top of the screen as the grid nears its ends, that item kept where it was. The strip of kinds shows jawd's counts; the search line takes words and the terminal's `from:`, `in:`, `since:` and `until:` as tokens (`LibrarySearch`); Enter opens as Files' Enter does, through Quick Look and `Opened`, and ⌘↩ goes to the message; the items on screen are named to jawd with `library.shown` as they change, as the terminal names them. What jawd's library rows don't carry yet, a voice message's waveform, a file's download state and a link's thumbnail, is the Mac design's P14.
- **Parity with the terminal** ([the parity plan](../docs/plans/2026-10-27-jaw-mac-parity-plan.md)): `parity.toml` lists each request and push of jawd's that the terminal uses and the app doesn't yet, with the plan's step that brings it. `make check-parity` fails when the terminal gains one the list doesn't have, or the app closes one the list still holds, so a step that lands takes its rows out.

## What it costs

Measured on 26 October 2026 on the build Mac (Apple M4 Max, 16 cores, macOS 27.0.1) with a Release build, against `jawd demo`'s made-up account of a million messages in 3,000 chats served by a release jawd, while it indexed that history for search and other builds kept the load average at 19 to 30. These are Mac-M1's first measurements; `make perf-mac` is still to come.

To measure, build in Release signed ad hoc with the hardened runtime off, as `build-mac release` does (`CODE_SIGN_IDENTITY=- ENABLE_HARDENED_RUNTIME=NO`): with the hardened runtime on, dyld now refuses the app's ad hoc frameworks as having different Team IDs. Built that way it has no jawd beside it, as `make mac`'s has, nor looks for cargo's as a debug build does, so `JAWD` names the jawd `--demo` starts.

| | Budget | Measured |
| --- | --- | --- |
| Launch to a usable chat list | 250 ms p99 with jawd running | 188 to 196 ms over five warm launches; 596 ms the first, cold |
| Opening a chat | 30 ms p99 | 33.4 ms p50, **54.8 ms** p99 over the first 20 chats |
| Memory | under 80 MB with a screen of text | 35 MB with the chat list and a chat drawn |
| Idle | no wake-ups but the clock's minute | **14** wake-ups in a quiet minute |
| App size | under 60 MB with the helpers | 44 MB |
| Scrolling with photos | no frame missed at 120 Hz: main-thread turns under 8.3 ms p99, hitches under 1 ms a second | **12.7 to 13.3 ms** p99 and **40 to 46 ms** of hitches a second in bubbles, **11.3 to 11.5 ms** and **21 to 24 ms** in lines; the same chat with nothing decoded, **11.6 to 12.1 ms** and **36 to 39 ms** in bubbles, **9.9 to 10.1 ms** and **10 to 12 ms** in lines |
| Scrolling the library's grid | the same | **16.1 to 18.6 ms** p99 and **98 to 114 ms** of hitches a second over 3,000 photos, from 44.0 to 44.4 ms and 488 to 492 ms before its tiles showed their pictures as their layers' contents |
| Memory with a screen of photos | under 150 MB; decoded pictures at most 64 MB | a footprint of 63 to 66 MB; separately, the cache's count of decoded pictures at its limit, 64 MB |
| Memory with a screen of the library | under 150 MB; decoded pictures at most 64 MB | a footprint of 65.3 to 70.3 MB after a fling through 3,000 photos, with the pane still shown, from 133 to 136 MB before; the cache's count of decoded pictures at its limit, 64 MB |
| Memory with no window open | under 25 MB | **59 to 61 MB**, the decoded pictures let go |

Where it falls short: opening a chat at p99, measured at a load of 25 to 30 with jawd's search index being built beside it, is to be measured again on a quiet Mac before it's called a defect; and the quiet minute's 14 wake-ups aren't yet accounted for. The keypress and a frame's apply aren't measured yet.

Scrolling with photos was measured on 31 October on the build Mac (an M4 Max MacBook Pro, macOS 27.0) with a Release build, at a load of 1.5 to 2.2, by `--bench pictures`, four times: on `--demo`, it waits for jawd to have the lake in Ana's chat with both previews, clones them as the previews of 120 messages, 165 pictures in photos of five shapes, albums of four, stickers and posters, each a file of its own so each is decoded, and flings through them at 6,000 points a second, down and up, timing every turn of the main run loop, in each look with its pictures and then with nothing decoded, its wells alone; then it measures the footprint on a screen of photos in bubbles, drawn from its pictures again, and with no window open, the app's closed and the bench's let go.

It misses its frame before any picture: with nothing decoded the transcript's turns are over 8.3 ms already, so its tiling and Core Animation's commits must get cheaper first, which the budgets plan is measuring on `mac-perf`. The pictures cost their own on top: in each run, 0.6 to 1.2 ms at p99 and 2 to 8 ms of hitches a second in bubbles, and 1.3 to 1.4 ms and 9 to 13 ms in lines, over half the hitches there; on 30 October, at a load of 6 to 10, they added 2 to 4 ms and most of the hitches over a chat with nothing decoded at 7.9 to 10.6 ms and 5 to 25 ms, so the build Mac's runs vary that much from day to day. The pictures' share alone would break the budget for hitches over a transcript within it, so it's for `mac-perf` too. The cells' own drawing is under 0.3 ms at p99 with pictures or without, so what costs is what a picture arriving sets off: the whole cell drawn again, its text with it, and uploaded again, and a Core Animation transition for each fade. The likely remedy is a sublayer for each picture whose contents is its decoded image, so one arriving neither draws the cell again nor uploads its text, and fades only its own layer. Decoding stays off the main thread, four at a time: 850 decodes for the 165 pictures over the two flings with them, as the cache keeps 64 MB.

The library's grid was measured on 2 November on the build Mac with a Release build by `--bench library`: on `--demo`, once jawd has the lake's previews, it clones them as the previews of 3,000 photos an hour apart, each picture files of its own so each is decoded, and shows them in a library pane of photos in a window 900 points square, its moves answered 4 ms later with what came into the window and what left it, one at a time and only the latest, as JawKit's client sends them, and flings at 6,000 points a second to the oldest and back, timing every turn of the main run loop. Its tiles drew their pictures in `draw(_:)`, bitmaps the image queue decodes in sRGB, so on the build Mac's display Core Animation's commit converted each to the screen's colours and resampled it on the main thread as it filled the tile's backing store, as the review's sample found: 44.0 to 44.4 ms at p99, 570 of about 1,165 turns over a frame, and 488 to 492 ms of hitches a second, at a load of 2 to 3, the footprint after the fling 133 to 136 MB. Given as its layer's contents, a tile's picture halved that, to 21.2 to 24.2 ms and 138 to 146 ms a second, but Core Animation then converted each as it committed, still on the main thread, keeping the copies, so the footprint rose to 188 to 191 MB. Decoded in its window's colours, a tile's picture is shown as it is: over 20 flings at a load of 1.4 to 6.7, 16.1 to 18.6 ms at p99 and 98 to 114 ms of hitches a second, the cache at its 64 MB, and a footprint after the fling of 65.3 to 70.3 MB, measured with the pane still shown, about 4 MB more than with the pane let go, as the earlier runs measured it. What's left is the grid's own: in a ten-second sample of the fling's main thread, Core Animation's commits took 424 ms and `NSCollectionView`'s layout 298 ms, making the cells that scroll in, and every cell on screen again after each move. A move's landing takes 3.8 to 4.7 ms at the median of each fling, against 1.5 ms when the tiles drew their pictures, so it misses the design's 2 ms p99 for applying a frame of updates on the main thread, because each landing reloads the grid's data and makes every cell on screen again. The grid misses both budgets, the frame's as the conversation does, and both are `mac-perf`'s with the conversation's. The conversation, measured beside it before and after, is as it was, its cells still drawing their pictures in sRGB: 12.5 to 13.1 ms at p99 and 43 to 50 ms of hitches a second in bubbles, 11.2 to 11.7 ms and 20 to 25 ms in lines, at a load of 1.8 to 3.5.

With no window open the decoded pictures go, and the cache keeps nothing until the window's back, but the footprint is still 59 to 61 MB, against 61 to 62 MB measured the same way on this step's code before the cache was emptied as the window closed. What holds it is the app's own window and panes, kept while it's closed, not the pictures: on 1 November, main, without this step, took 42 MB in a text session with its window open and 42 MB with it closed, so closing the window frees nothing there either.

The footprint and the cache's count of decoded bytes are separate facts, not one inside the other: the cache counts each picture's decoded pixels, four bytes each, whether or not they're resident. On 1 November, on a screen of photos, vmmap showed the decoded pictures as 67 MB of address space with only 5 MB of it resident, and a screen of text alone took 41 to 48 MB.
