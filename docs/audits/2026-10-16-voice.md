# Audit: voice recordings (jaw-voice)

Range: origin/main..686c0e8 (1ade72e, 686c0e8) in `voice`, 2026-10-16, third round. Auditor: database-expert.

The change adds `crates/jaw-voice/`. Nothing in jawd, the engine, SQL, `jaw.db` or `session.db` changes. The branch was rebased onto a newer `origin/main`, and its own diff is only the crate, `protocol/README.md`, `scripts/check-data-audit.py`, the workspace's `Cargo.toml` and `Cargo.lock`, and one CI step.

Two parts fall under the data layer. The first is the recording's file in `crates/jaw-voice/src/record/`, which becomes an outgoing voice message's media. The second is how the crate tells its caller that the file exists, through the `Recorded` event in `src/lib.rs`, which acts as the recording's acknowledgement. The rules the change touches are:

- A media file is synced and put in place before a row points to it.
- A file is deleted only after a synced commit stops pointing to it.
- Nothing in flight is lost on a crash, a power cut or a full disk.
- Files and queues are bounded and counted.
- Every rule has a test.

Earlier rounds found these problems, all now fixed:

- F1 (first round, at 45b28ff): a recording replaced, and could then delete, a file already under its name.
- F2 (first round): a recording's end could be dropped when the event channel was full.
- T1 and T2 (first round): no test for a microphone failing mid-recording, or for a full disk.
- F3 (second round, at 0489f12): a recording's end could still be dropped behind a held refusal, and a refusal was the same event as a failure.

Every finding marked data loss or inconsistency is fixed, and each fix has a test that fails when the fix is reverted.

## Findings

### Data loss

None remain.

**F1 (first round), fixed.** `PartFile::create` (`record/file.rs:30-50`) refuses a name that's taken, and opens the `.part` with `create_new`, refusing a stale one. `finish` (`file.rs:54-78`) does four things in order:

1. Syncs the file (`F_FULLFSYNC` on macOS, measured).
2. Puts it in place with `fs::hard_link`, which fails with `EEXIST` rather than replacing anything.
3. Removes the `.part`.
4. Syncs the folder.

On a failure, it removes the final name only if its own link made it. After a crash or power cut, the possible states are the `.part` alone, both names on the same whole, synced file, or the final name alone. Each is whole, and jawd removes stale `.part` files at start.

Tests: `a_name_thats_taken_is_refused_when_recording_starts`, `a_file_that_appears_under_the_name_meanwhile_is_left_as_it_was`, `a_part_left_by_an_earlier_recording_is_refused_rather_than_overwritten`, `a_killed_recording_leaves_no_half_file_under_its_name` and `a_full_disk_fails_the_recording_and_leaves_nothing`.

### Inconsistency

None remain.

**F2 and F3, fixed.** The events now say exactly one thing each:

- `Event::RecordingRefused` (`lib.rs:140-143`) means a recording asked for didn't start. It carries the real reason: a taken name, a stale `.part`, no microphone, already recording (checked in `lib.rs:376-379` before playback is touched), or an end not yet read.
- `RecordingFailed` now only ends a recording that started.

What finds the channel full is held (`Held`, `lib.rs:304-318`) in three slots:

- **`playback`:** the newest state is kept.
- **`refusal`:** the newest is kept. A refusal changes nothing, so a newer one may replace it.
- **`ends`:** never truncated or replaced. A `record` is refused while an end is held, so this slot holds at most one.

Held events are offered again every tick, and the command channel is bounded at 64 (`Error::Busy`). Every recording that starts has exactly one end, and the end reaches the caller.

Tests: `a_recordings_end_is_held_for_a_caller_that_falls_behind_and_never_dropped` and `refusals_held_while_the_caller_is_behind_never_push_out_a_recordings_end`, which runs the second round's probe sequence. A stress probe (below) found no counterexample.

### Tests

Each rule the change touches has a test:

- **The file is whole under its name, or nothing is there:** finished, killed, cancelled, empty, refused at start, failed rename or link, full disk.
- **A file the recording didn't make is never replaced or removed:** a taken name, one that appears meanwhile, a stale `.part`.
- **What came before a microphone failure is kept:** `a_microphone_that_fails_midway_keeps_what_came_before`.
- **A recording's end is never dropped:** the two held-event tests.
- **Bounds:** the length cap, the event and command queues, and the counted overruns, gaps and dropped events.

### Unpredictable performance

None that breaks a budget. Finishing blocks the audio thread for two full flushes, about 12 ms for a 2.7 MB recording, after the recording has ended.

### Hygiene (stand as follow-ups)

- **H5 (first round).** A folder-sync error after the file is in place throws away a whole synced recording (`file.rs:69-75`). It's consistent, since the protocol says nothing is kept after `failed`, and the deleted file is always the recording's own.
- **H6 (second round), done.** `Recorder::start` creates the `.part` and writes the headers before opening the microphone (`record/mod.rs:73-76`). So a taken name or a stale `.part` never lights the microphone, and a microphone that can't open still leaves nothing (`a_microphone_that_cant_be_opened_refuses_the_recording_and_leaves_no_file`).
- **H7 (second round), carried to jawd as J9.** Recording needs hard links.
- **H8. The caller can't match a `record` to its outcome.**
  - A refusal doesn't name the request it refuses, and a held refusal is replaced by a newer one.
  - A recording that starts has no event of its own. Its first sign is a `Recording` tick, and ticks are dropped while anything is held.
  - An end can overtake a held refusal, since ends are released first.

  None of this loses or misstates data, because files exist only for recordings that started, and each of those ends exactly once. But jawd can't reply exactly to `voice.record` if it sends a second `record` before the first is answered. Either jawd keeps one `record` outstanding (J10), or the crate adds a `RecordingStarted` event held like an end, or a caller's token echoed in `RecordingRefused`.

### Follow-ups for jawd's wiring (not this branch)

- **J1.** Give every recording a fresh path that is never reused, inside the account's folder (mode 0700), for example named by the message ID jawd makes up front.
- **J2.** At start, after taking `jaw.lock`, delete the `.part`s in the recordings folder (`part_path`), since the crate refuses to record over one. Decide whether a stopped, unsent recording survives a restart. If it does, jaw owns it: give it a row, committed synced after `Recorded` and before `voice.stop` replies. If it doesn't, delete the finished files no row points to.
- **J3.** Commit the outbox row that points at the file synced (`FULL`, `fullfsync`) before `voice.send` replies. Delete the file only after the synced commit that stops pointing to it, once the message is sent or cancelled. The cache never evicts it while it's unsent.
- **J4.** Reply to `voice.stop` only after `Recorded` arrives. Treat `Error::Busy` from any `Voice` method as a reply-with-error or a retry, never as success.
- **J5.** On a graceful shutdown during a recording, call `stop_recording` and wait for `Recorded`. Dropping `Voice` cancels the recording and discards anything held.
- **J6.** Put `Stats` (overruns, dropped events) and each recording's `gaps` in `jawd status` and the log. Check free space for at least the cap's size before a recording starts.
- **J7.** Send the played receipt off jawd's own accepted `voice.play`, not off a `Playing` event, which can be superseded while jawd is behind.
- **J8.** Give 1ade72e the trailer `Data-Audit: docs/audits/2026-10-16-voice.md`, since it touches `record/`, `lib.rs` and `tests.rs`. 686c0e8 touches only `protocol/README.md`. Run `make check-audit` before pushing.
- **J9.** Check once at start that `hard_link` works in the recordings folder, and say so in `jawd status`. A filesystem without hard links would otherwise fail every recording at the end.
- **J10.** Keep at most one `record` outstanding. Take a `RecordingRefused` or the first `Recording` tick as its answer before sending another (see H8).

## Measurements

All of this ran in a scratch clone (`/tmp/jaw-voice-audit` at 686c0e8) on the owner's M-series Mac (APFS, internal SSD), with fake devices only. Nothing played and no microphone opened.

- **The crate's tests:** `cargo test -p jaw-voice` gave 36 passed and 2 ignored (the child processes of the kill and full-disk tests). Three runs in a row were green, at about 2.0 s each.
- **The new tests fail without their fixes**, checked by reverting each fix in the scratch clone:

  | Fix reverted | Test that fails |
  | --- | --- |
  | `hard_link` back to `rename` (second round) | `a_file_that_appears_under_the_name_meanwhile_is_left_as_it_was` |
  | Taken-name check removed (second round) | `a_name_thats_taken_is_refused_when_recording_starts` |
  | Held ends dropped (second round) | `a_recordings_end_is_held_for_a_caller_that_falls_behind_and_never_dropped` |
  | Refusals back in the ends slot with `truncate(1)`, this round's F3 regression | `refusals_held_while_the_caller_is_behind_never_push_out_a_recordings_end` |
- **The second round's F3 probe, re-run:** 1 `Recorded`, 0 `RecordingFailed` and 1 `RecordingRefused`, with the file whole under its name. In the second round it gave 0 `Recorded`.
- **Stress probe** (scratch clone only), three runs: 30 rounds, each recording to a fresh name, with random choices of these:
  - a flood of 256 playback failures;
  - a `record` while recording;
  - stop or cancel;
  - a quick second recording;
  - draining only one round in three.

  The final drain gave 10, 10 and 11 `Recorded`, 1, 1 and 0 `RecordingFailed`, 3 `RecordingCancelled` and 11 `RecordingRefused`, with 1,568 progress or superseded events dropped. Each time, the files under their names matched the `Recorded` count exactly, and 0 `.part` files remained.
- **From the first round, unchanged:**
  - `File::sync_all` costs what `F_FULLFSYNC` costs: 7.11 ms against 6.89 ms median, and 0.76 ms for plain `fsync`, over 30 runs on 2.7 MB.
  - The whole finish takes 12.4 ms median.
  - The measure example gave a five-minute note at 23.0 kbit/s with 0 samples lost, and recording CPU at 2.1% of a core.

## Verdict

Nothing marked data loss or inconsistency remains, and every rule the change touches has a test that fails without its fix. H5 and H8 stand as follow-ups, and J1 to J10 are for jawd's wiring, J8 before this lands.

Verdict: approved
