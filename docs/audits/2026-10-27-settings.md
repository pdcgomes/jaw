### Hygiene (follow-ups; none blocks)

- **H1. The table's names and values have no bound, and the `CHECK`s are free only until migration 13 merges.** This is the final review's first question.
  - **Where:** `store/schema.rs:738` to `:744`.
  - **What happens:** nothing outside jawd reaches the table's text today. The domain can only be `jaw`, since any other client is refused before the writer; the keys are two names; and the values come from closed lists, each under 20 bytes. So the table is bounded by jawd's code alone.

    - Adding the `CHECK`s after the merge takes a rebuild of a table of jaw's own, in the twelve steps; before it, it's three lines and the lock's hash.
  - **Fix:** take the text below as migration 13, with its lock line `13 schema 5613326189c227dc15357bdd7b15dc5d5d2f8dc4128a6ada442f20e22af3ce06`, and adopt the second table test printed below.
```sql
    CREATE TABLE settings (
        domain TEXT NOT NULL CHECK (octet_length(domain) BETWEEN 1 AND 64),
        key TEXT NOT NULL CHECK (octet_length(key) BETWEEN 1 AND 64),
        value TEXT NOT NULL CHECK (json_valid(value) AND octet_length(value) <= 4096),
        at INTEGER NOT NULL,
        PRIMARY KEY (domain, key)
    ) STRICT, WITHOUT ROWID;
```

- **H2. Nothing tests the table's `STRICT`, or `at`'s `NOT NULL`.**
  - **Where:** `store/schema.rs:742` and `:744`.
  - **What happens:** migration 13 without `STRICT` and with `at` nullable, its lock line changed to match (`ac0959cb…`), passes all 18 of the settings, store and schema tests I ran it against. Without `json_valid` (`e287bddd…`), two store tests fail.

- **H3. The settings arm's guards for a reply its own drain leaves waiting have no test.**
  - **Where:** `sock.rs:355` and `:361` to `:364`.
  - **What happens:** two switches survive every test.
    - With the push sent over a reply the drain left waiting (`push-over-waiting`), `Owed::wait` (`:149`) would replace that reply, so the interface would never hear its answer.
    - With the settings not marked changed then (`no-mark-changed`), the push would wait for the next change.
    - Both paths need a reply to land in the connection's channel between the select's poll of answers and its poll of the settings, with the queue to the interface full. The bias polls answers first, so no test reaches them.
    - They're right as written, and neither touches what jaw.db keeps.
  - **Fix:** a test-only pause before the drain, as `gate_next` pauses a change, so a test can put a reply in the channel with the queue full; or the arm's body as a function a test can give a full queue.
- **H4. A half-closed connection owed nothing can end without the latest settings.**
  - **Where:** `sock.rs:246` and `:273`, against the README's "A connection always ends on the latest" (`protocol/README.md`, Settings).
  - **What happens:** I read this rather than ran it. It's the path round two of the interface-state audit showed for layouts with P1b (its H12).

    - A change made while the push waited is never pushed to it.
    - Nothing on disk is wrong. jaw doesn't half-close, and `jaw settings` reads its answer and goes.
  - **Fix:** the README's sentence for half-closed connections, as H12's fix gives it for layouts; or, before ending a half-closed connection, send the latest settings when the channel holds a change it hasn't been told.
- **H5. The design's list of tables doesn't name `settings`.**

### The two questions

- **Should `settings` read like `interface_state`?**
  - **`at`:** keep it. Eleven of jaw.db's other tables call a row's time `at` (`inbox`, `messages`, `quarantine`, `tombstones` among them), and only `interface_state` says `updated_at`; the rest name a particular event, such as `created_at` or `read_at`. `settings.at` is when the value in effect was chosen, which asking for it again doesn't move; that's tested.
  - **The length `CHECK`s:** add them now (H1). Without them nothing is wrong today, as H1 says, so it doesn't block. But they'll never be cheaper, and the hello name they'd bound is the one `interface_state` already bounds.
- **A second failure replacing the domain's quarantine row:** right as it is.
  - A failed change is refused to the interface that asked, with "nothing changed" and why, so nothing acknowledged is lost. The row is what's left to read.
  - One row per domain keeps the quarantine bounded however often a change fails. Main's layouts do the same, one row per interface and key.
  - Nothing replays a `settings` row (the quarantine's only deletes are by `inbox`, `history_raw` and `merge`), so a stale one can never be applied over newer settings.
  - As with layouts (interface-state's H6), the row outlives a later success. Whoever reads the quarantine should take it as the last change refused for the domain, not one waiting. The design's settings Storage section could say so in a sentence.

```rust
    async fn a_change_whose_second_setting_cant_be_kept_keeps_neither_and_publishes_nothing() {
        let (home, store, settings) = opened();
        let outside = rusqlite::Connection::open(home.path().join("jaw.db")).unwrap();
        // The settings are kept in the order of their names, so the theme is the second.

                "CREATE TRIGGER refused BEFORE INSERT ON settings WHEN NEW.key = 'theme'
                BEGIN SELECT RAISE(ABORT, 'refused'); END",
            )
            .unwrap();
        let heard = settings.subscribe(TERMINAL).unwrap();
        let e = refused(&settings, json!({"messages": "irc", "theme": "nord"})).await;
        assert_eq!(e.code, code::INTERNAL, "{}", e.message);
        assert_eq!(store.setting(TERMINAL, "messages").unwrap(), None, "the first isn't kept without the second");
        assert_eq!(settings.current(), Terminal::default());
        assert!(!heard.has_changed().unwrap(), "nothing published");
        outside.execute_batch("DROP TRIGGER refused").unwrap();
        let now = set(&settings, TERMINAL, json!({"messages": "irc", "theme": "nord"})).await.unwrap();
        assert_eq!(now, Terminal { theme: "nord".into(), messages: Messages::Irc }, "asked again, both are kept");
        assert_eq!(store.setting(TERMINAL, "messages").unwrap().as_deref(), Some("\"irc\""));
```
