### H35 (`2fc150a`)

`NO_FILE` (`store/write/media.rs:277`) now applies only when no `media_files` row with the copy's hash has a `path`, the check `UPLOADED` already had (`:270`). Its plan is a search of `media` by primary key and, correlated, of `media_files` by primary key (`plans.txt:990`).

Whether a copy shows its file comes from `media_files.path` alone, never from `media.state`, so the question is whether `state` and `error` can disagree with the file for good. They can't:
- **Never `gone` beside its file.** `NO_FILE` is the only statement that sets `gone` (the migration only carries it over), and it now never does while the file is in place. A copy made `gone` before the file came is put back to `remote` with no error by `Placed`'s `READY` (`:241`), which every placing of a file runs for every copy with its hash.
- **Never shown present without its file.** The check reads only `media_files.path`, which is set only once the file is whole and fenced (`Placed`), and goes only in a synced commit before the file is removed (`Drop`). A thumbnail or previews alone make a `media_files` row with no `path`, and the check's `f.path IS NOT NULL` keeps those from counting (but see H37).
- **What the skip leaves settles.** The copy stays `remote` and wanted with no error. Its job takes a file in place without downloading it (`media/schedule.rs:423`) and settles it `remote` (`:412`), which ends the want. If the file has gone by then, the job downloads it, and asks the phone again if the server no longer has it, as for any copy.
- **No copy waits for the phone beside its file.** `ASKED_PHONE` needs the copy `downloading`, a download finds a file already named by its hash and places it without asking the engine (`media/fetch.rs:126`), and `READY` takes any copy waiting for the phone back to `remote` once its file is placed.
- **Replays.** The skipped answer changes nothing, and its inbox row is drained, so the answer converted twice still changes nothing twice. The `retried_at` it leaves on the copy matters only once the copy waits for the phone again, which F2 already covers.

Switched off (R1, the code before `2fc150a`), the new test `a_no_file_for_a_copy_whose_file_is_already_in_place_changes_nothing` fails as the commit says: the copy ends `gone`, wanted by nothing, with "your phone no longer has this file", at version 11 against 10. Only that test and the plan test, by its pinned text, fail of the 261 media and store tests.

The check's `f.path IS NOT NULL` counts most, since every photo whose instant preview is drawn has a `media_files` row with no `path` until its file comes. Taking any row as the file in place (R2) re-opens I8: the "no file" is skipped, and the phone is asked again. The whole suite catches it in one test only, K1's `an_answer_left_behind_a_backlog_at_a_stop_is_kept_when_sync_starts_first`, which failed 6 of 6 times ("asked again 1 times", the copy left `waiting_for_phone`), and passed 5 of 5 on the head. K1's two variants without a backlog passed 5 of 5 each with R2, since their answer converts before the thumbnail is drawn. So the rule is tested, but only by the order the 2,000 rows ahead give it (H37).

## What was asked, checked

### The copies backfill

**How it works.** `store/write/copies.rs` is run by main's backfill driver (`store/write/links.rs:54-100`), 64 steps to the writer at a time (`sync/backfill.rs`), from the row migration 19 leaves. A step:
1. reads the next 16 messages by key, up to the newest at the upgrade, reading `detail` and `deleted` but no raw protobuf (`NEXT_COPYLESS`, `:36`);
2. takes the first that brings a file, isn't deleted and has no SD copy: its raw protobuf converts as it would now, and its copy is written with nothing wanting it, by the upsert a message arriving uses (`media::upsert`), with a new version and its event;
3. ends there, since `COPYING` is zero, and the next step goes on from that message.

An HD copy an earlier jawd kept as a photo of its own keeps showing that file, and also becomes its photo's HD copy (an `Amendment::Hd`). One whose photo jaw.db never had waits in `pending` for it.

**Checked:**
- **Which messages it finds.** It finds one by `detail` alone, `instr(detail, '"media":')`. Every jawd since the first converter (`7fcd8eb`, 16 October) writes that key for photos (instant ones too), videos, GIFs, video messages, voice messages, audio files, documents and stickers, empty if WhatsApp said nothing of the file. Those are exactly the kinds the branch's converter gives a copy (`convert::kinds::copy`). A message an earlier jawd kept as unknown has no such key. `kinds` converts it again and, since `c0a83ea`, writes its copy, whichever of the two backfills reaches it first. An edit standing in for its message carries no copy, arriving now as well.
- **Resumable and idempotent.** A step's copies and how far it got commit in one transaction. A message with its copy is passed over, and the upsert's merge rules change nothing twice. N24, the look without its check for a copy already there, changes no test's outcome, since the step then writes nothing.
- **Safe to kill.** The builder's test copies jaw.db after every commit (`VACUUM INTO`) and runs on from each copy. I also SIGKILLed a running jawd 20 times on a copy of the million-message jaw.db:
  - the first kill came before migration 19 committed, and left jaw.db at version 18;
  - the rest landed across the backfill, from 1,744 messages in to 952,659;
  - it then ran to the end, and left the 1,000,944 messages held before migration 19 exactly as a jawd never killed left them: 166,667 copies with everything they say, each message's events, `pending`, quarantine, and `quick_check` ok.
- **Failures.** A raw protobuf that doesn't read leaves the message as it is. A conversion that fails or panics goes to quarantine with the raw protobuf, once per message, since `(source, ref)` is unique. A full disk fails the step, which is tried again (N9).
- **Either state.** `media.fetch`, `media.save` and `media.cancel` of a message the backfill hasn't reached give it its copy first, in the live lane, made durable by the fetch's synced want. On the million-message copy, `media.fetch` of the newest photo succeeded while the backfill had 907,667 messages left.
- **Reported.** The status answer's `copies_backfill` is how many messages the backfill has still to look at (`upto - after`). In a debug jawd it fell from 907,667 to 0 in 31 s.
- **What it adds to migration 19.** One insert into `backfills` from `sqlite_sequence`, at constant cost, so migration 19 stays a schema step, as main's 14, 15 and 16 add their backfills' rows. Migration 19 isn't on main, so its text may still change: its lock line is `19 schema cc0f2d3a…`, and lines 1 to 18 are main's. No other branch in flight adds a migration.
- **Showable.** A debug jawd on a copy of that jaw.db, watched through `jaw.sock` as an interface would:

- **I8, a later job's re-take (K4).** A copy waits for the phone. The owner opens it, and its new job's download waits behind another in a one-worker lane. The first ask's "no file" arrives.
  1. `NOT_UPLOADED` takes the downloading copy: `gone`, "your phone no longer has this file".
  2. The download finds the file gone from the server, and `gone()` notes the ask. The note changes nothing, since the copy isn't downloading any more, so the job returns without settling (`media/fetch.rs:275`, `media/schedule.rs:403`).

Media's struct fields conflict textually with it, and `media.go:161` and `:385` use `e.client` directly, which won't compile once it's a pointer. Use `e.cli()`, read once per command.
- **The events kept.** `handleFrom` passes on a retired client's events only if `mustKeep` says jawd must store them: messages, app state, push names, groups, pictures and receipts. Media's `*events.MediaRetry` is acked with a seq, since the phone won't upload unasked. Add it to `mustKeep`. Nothing fails if it's left out.
- **The failing demo engine** (`engine/failing.rs`). It passes media's commands to the demo. While WhatsApp is cut off, `needs_whatsapp` fails them retryably, as it should. With the phone offline, though, the demo's phone still answers a `MediaRetry` at once. To match the real phone, hold it as `HistoryRequest` is held; that's for the failure tests' realism, not the data's.

### Inconsistency

- **I7. Copies for what jaw.db held before migration 17: none, ever.**
  - **Where:** migration 17 (`store/schema.rs`) copies `media`, which no jawd on main wrote. Copies are written only:
    - as a message arrives (`store/write.rs:1877-1890`);
    - for an HD copy (`:2145`);
    - by `kinds`, which converts again only what an earlier jawd couldn't show (`store/write/kinds.rs:34-35`).
  - **What happens (K8):** a photo stored as main stores it, with its message, `detail` and raw protobuf and no copy:
    - its row shows only its size and type;
    - nothing reports it to media, as the read path reports only rows with a copy;
    - `media.fetch` answers error 3, "message 3EB0BEFORE has no a file";
    - nothing makes a copy after the backfills run.
  - **When:** for every photo, video, voice message, document and sticker in the owner's jaw.db at the upgrade, which m2-content's audit counted at 86,989 messages. Each gets its copy only if the phone sends it again.
  - **Why it matters:**
    - The raw protobufs are the source of truth, and the same message gets a copy or not depending on whether it was stored before or after the upgrade.
    - A replay of an old message adds a copy that wasn't there.
    - The design's Migrations make "anything that can be a backfill" one.
  - **Fix:** a backfill, `copies`, like main's `kinds`:
    - its row added to `backfills` in the next migration, a schema step (`'copies', 0, seq FROM sqlite_sequence WHERE name = 'messages'`);
    - each step reads messages by key up to `upto`, decodes the raw protobuf of one whose kind has a file, and upserts its SD copy with nothing wanting it, as history's are;
    - deleted and view-once messages skipped, as on arrival;
    - steps within 3 ms, resumable, and idempotent through the upsert;
    - its cost on the million-message bench written beside it.

    `kinds::NEXT_UNSHOWN` shows the shape. Test: K8 run until the backfill is done, plus the backfill's own resumable and idempotent tests.
- **I8. A "no file" answer to an earlier ask is undone by a later job's next run.**
  - **Where:** `media/fetch.rs:275` returns without settling when the note changes nothing, and `media/schedule.rs:403` ends the job there. The want stays set, so the copy is taken again, and `DOWNLOADING` (`store/write/media.rs:226-227`) clears what the phone said.
  - **What happens:** under "I6: kills, both orders" above; K4 ends `waiting_for_phone` with two asks, 3 of 3.
  - **When:** the owner opens a photo whose phone was asked a moment ago, while downloads are busy. That's a catch-up after time offline, when files gone from the server are likeliest.
  - **Fix:** a "no file" ends the want it meets (F1). Or a job whose note is refused at an unchanged want settles it, leaving the state as it is. Test: K4.
- **I9. An answer converted after a start has wanted its copy again changes nothing.**
  - **Where:** `Restarted` (`store/write/media.rs:507-523`, `:289-291`) and `NOT_UPLOADED` (`:266-267`); their order at a start (`media/mod.rs:248-250` against `main.rs:484`).
  - **What happens:** under "I6: kills, both orders" above. K1b at the store ends `remote` and wanted; K1 with media started first ends waiting for the phone, 2 of 2.
  - **When:** a stop or crash while the converter is behind and a "no file" waits in the inbox, then a start where media reaches `Restarted` before the converter reaches the answer.
  - **Fix:** `NOT_UPLOADED` also takes a copy wanted again since its ask (F2), ending its want as F1 does. Or the start wants copies again only once the inbox rows it found are converted. Test: K1b, and K1 in the rig's order.

### Unpredictable performance

- **P8. Every commit wakes media's scheduler and its cleaner, and their reads meet the window's read of that commit.**
  - **Where:**
    - The scheduler looks on every commit, at most every 25 ms (`media/schedule.rs:282-287`, `LOOK_EVERY`). Each look is three reads at interactive priority, the windows' own (`:266-268`), whether or not anything is wanted.
    - The cleaner looks on every commit too (`media/cache.rs:214-220`), with two background reads.
  - **Measured:** under "Measurements". In a full jawd on a million messages, a lone message from its commit to the interface took:
    - 1.90 to 3.32 ms at p50 on the head, in six runs;
    - 1.26 to 1.53 ms on main, in six runs alternating with them;
    - 1.19 to 1.47 ms on the head with both looks switched off (M21, M22), in three runs.
  - **Why it matters:** the budget is 5 ms at p99 for every message. A fifth to a third of it goes at p50, on a path with no media at all. The p99s were noise at this load, so I can't say it breaks the budget.
  - **Fix:** wake the scheduler when a want is written, rather than on every commit. Media's own steps and the upsert of a message with a copy are the only writes that set one. Wake the cleaner when `media_drop` gains a row. Then measure as I did.

/// Probe K1: the phone's answer that it has no file, acked into the inbox before a stop and not yet
/// converted, meets the next start, which wants the copy again; the phone is off by then. `ahead`
/// inbox rows wait before the answer; `media_first` starts media before sync, as the rig does,
/// rather than after, as main.rs does.
fn k1_answer_left_in_the_inbox(ahead: usize, media_first: bool) -> (String, Option<String>, usize) {
    let home = Arc::new(tempfile::tempdir().unwrap());
    let lake = Picture::lake(640, 480);
    as_a_jawd(async {
        let store = Store::open(home.path()).unwrap();
        crate::sync::running(&store).await.unwrap();
        let event = World::default().photo(&lake, ANA, ANA, "3EB0LEFT", now_ms(), "");
        let Some(pb::event::Kind::Message(message)) = event.kind else { unreachable!() };
        let web = crate::convert::web_message(&message).unwrap();
        let me = crate::convert::Me::new([demo::ME.to_string()]);
        store.apply(Lane::Live, crate::convert::message(&web, &me, true)).await.unwrap();
        let (n, wanted): (i64, i64) = store
            .reads()
            .query(Priority::Interactive, |db| {
                Ok(db.query_row("SELECT message, wanted FROM media", [], |r| Ok((r.get(0)?, r.get(1)?)))?)
            })
            .await
            .unwrap();
        let downloading = Step::Downloading { message: n, variant: "sd" };
        let asked = Step::AskedPhone { message: n, variant: "sd", wanted, at: now_ms() };
        store.apply(Lane::Live, vec![Change::Media(downloading), Change::Media(asked)]).await.unwrap();
        for k in 0..ahead {
            let text = demo::text(ANA, ANA, &format!("3EB0AHEAD{k:05}"), now_ms(), "ahead of the answer");
            let Some(pb::event::Kind::Message(m)) = text.kind else { unreachable!() };
            store.inbox("message", now_ms(), m.encode_to_vec(), None);
        }
        let answer = pb::MediaRetried {
            id: "3EB0LEFT".into(),
            chat: ANA.into(),
            result: pb::media_retried::Result::NotFound as i32,
            timestamp_ms: now_ms(),
            ..Default::default()
        };
        store.inbox("media_retry", now_ms(), answer.encode_to_vec(), None);
        for _ in 0..4_000 {
            if store.count("inbox").unwrap() as usize == ahead + 1 {
                break;
            }
            tokio::time::sleep(Duration::from_millis(5)).await;
        }
        assert_eq!(store.count("inbox").unwrap() as usize, ahead + 1, "the answer waits in the inbox");
    });
    as_a_jawd(async {
        let store = Store::open(home.path()).unwrap();
        crate::sync::running(&store).await.unwrap();
        let engine = DemoEngine::with(vec![demo::connected()]);
        let world = engine.world();
        world.phone(Phone::Silent);
        let _ = world.photo(&lake, ANA, ANA, "3EB0LEFT", now_ms(), "");
        world.expire(&lake.direct_path);
        let (events, incoming) = mpsc::channel(1024);
        let supervisor = Supervisor::spawn(Arc::new(engine), events, Backoff::default());
        let live: crate::sync::Shared = Arc::default();
        let (pushes, _) = broadcast::channel(256);
        let pipeline = jaw_media::Media::new(jaw_media::Config {
            previews: jaw_media::Durability::Derived,
            ..jaw_media::Config::default()
        });
        let sync = crate::sync::run(
            incoming,
            store.clone(),
            live.clone(),
            pushes.clone(),
            Some(supervisor.clone()),
            home.path().to_path_buf(),
        );
        let _media = if media_first {
            let media =
                Media::start_with(store.clone(), Some(supervisor.clone()), home.path(), &live, &pushes, Config { phone_wait: Duration::from_secs(60), ..quick() }, pipeline)
                    .await
                    .unwrap();
            tokio::spawn(sync);
            media
        } else {
            tokio::spawn(sync);
            Media::start_with(store.clone(), Some(supervisor.clone()), home.path(), &live, &pushes, Config { phone_wait: Duration::from_secs(60), ..quick() }, pipeline)
                .await
                .unwrap()
        };
        let read = || {
            let reads = store.reads().clone();
            async move {
                reads
                    .query(Priority::Interactive, |db| {
                        Ok(db.query_row("SELECT state, error FROM media", [], |r| {
                            Ok((r.get::<_, String>(0)?, r.get::<_, Option<String>>(1)?))
                        })?)
                    })
                    .await
                    .unwrap()
            }
        };
        let mut last = read().await;
        for _ in 0..1_500 {
            last = read().await;
            if !matches!(last.0.as_str(), "remote" | "downloading") && store.count("inbox").unwrap() == 0 {
                tokio::time::sleep(Duration::from_millis(1_500)).await;
                last = read().await;
                break;
            }
            tokio::time::sleep(Duration::from_millis(20)).await;
        }
        let asks = world.asked().iter().filter(|k| matches!(k, pb::command::Kind::MediaRetry(_))).count();
        (last.0, last.1, asks)
    })
}

/// Probe K3: answers delivered twice, and an old one after a newer: each copy stays as the phone
/// first said, nothing downloads twice, and nothing's version moves.
#[tokio::test(flavor = "multi_thread")]
async fn k3_answers_twice_or_late_change_nothing() {
    use pb::media_retried::Result as R;
    let rig = rig(Config { phone_wait: Duration::from_secs(600), ..quick() }).await;
    let lost = Picture::lake(640, 480);
    rig.world.expire(&lost.direct_path);
    rig.world.phone(Phone::Lost);
    rig.photo(&lost, ANA, ANA, "3EB0LOSTTWICE").await;
    rig.until(ANA, "3EB0LOSTTWICE", "gone", |row| row["media"]["state"] == "gone" && row["media"]["thumbnail"].is_string()).await;
    rig.until_nothing_wanted("settled").await;
    tokio::time::sleep(Duration::from_millis(300)).await;
    let row = rig.row(ANA, "3EB0LOSTTWICE").await;
    rig.world.deliver(k_answer("3EB0LOSTTWICE", R::NotFound, "")).await.unwrap();
    rig.world.deliver(k_answer("3EB0LOSTTWICE", R::GeneralError, "")).await.unwrap();
    rig.k_converted("3EB0AFTER1").await;
    let again = rig.row(ANA, "3EB0LOSTTWICE").await;
    eprintln!("k3 lost: {} then {}", row["media"], again["media"]);

### The 16-job cap and the asked-first rule

- A copy is never done by two jobs at once.

**What doesn't:**
- **P6:** an asked copy whose own job was taken in the background waits for that job, whose writes stay in the background lane.

### Inconsistency

- **I6. The phone's answer is lost when it's converted before the job notes that it asked.**
  - **Where:** `media/fetch.rs:210`, `:248-253`, with `store/write/media.rs:246-254`.
  - **What happens:**
    1. A copy that arrived live, which nobody asked for, finds its file gone from the server.
    2. Its job sends `MediaRetry`, then notes `AskedPhone` in the copy's lane, now the background lane, which waits behind history and the WAL's bound.
    3. The phone's answer comes through the inbox and is converted in the live lane.
    4. If it commits first, `NOT_UPLOADED` (`WHERE state = 'waiting_for_phone'`) finds the copy still `downloading` and changes nothing.
    5. The note then makes the copy `waiting_for_phone`. Two minutes later the phone's silence leaves it `expired`, "your phone didn't answer when jaw asked it to send this file again".
    6. The phone had said it no longer has the file (`gone`), or why it couldn't (`expired`, with its reason).
  - An upload answer survives either order, since it moves the want on. Before `99bafcd` both went live, in the order they were made.
  - **Reproduced:**
    - **A2,** at the store, in the order the lanes allow: the copy ends `waiting_for_phone` with no error, and in the other order `gone`, "your phone no longer has this file".
    - **A2b,** in a running jawd. Background work is held behind the WAL's bound while the phone, asked, answers that it has no file. The answer is converted at once, and the copy ends `expired`, "didn't answer".
  - **When:** a live photo, sticker or voice note whose file the server no longer has, which is likeliest in a catch-up after long offline, when history holds the background lane longest.
  - **Why it matters:** an out-of-order arrival changes the outcome, and what the phone said, acked and converted, is dropped. The copy then tells the owner the opposite of what happened.
  - **Fix:** note the ask before sending it, live or synced, so no answer can come first. A failed send then expires the copy as now. At the least, note it live, as before `99bafcd`. Test: A2 and A2b.

### Unpredictable performance

- **P6. An interface's ask for a copy whose window's job is running waits for that job, which writes in the background lane.**
  - **Where:** `media/schedule.rs:277-283`, where the asked copy is passed over while its key is being done, and `media/fetch.rs:93`, where the job names its file in the lane it was taken in. `media.fetch` promotes the download (`media/mod.rs:426`), but the file's row, its previews and its settle stay in the background lane.
  - **Reproduced (A1):**
    1. A window shows a history photo, and its download starts.
    2. Background work is held behind the WAL's bound, and the interface asks for that photo.
    3. 10 s later it's still `downloading` at half, its file on disk.
    4. It's drawn 0.45 s after the hold ends.
  - **When:** the most common ask there is: a window shows a photo, and the owner opens it.
  - **Why it matters:** the commit's rule is that what an interface asks for is taken first and written live. Its test `a_file_a_window_began_downloading_is_named_at_once…` uses another message with the same file, not the same copy, so nothing tests where the rule breaks.
  - **Fix:**
    - let an asked job start beside the background one for the same copy (key the jobs by copy and priority; both share the download and image jobs), or
    - have `media.fetch` raise a flag the running job reads at each write.

    Test: A1.
- **P7. Newest first, a copy that arrives while windows show history waits behind everything they show after it. Judged: not acceptable for what arrives live.**
  - **Where:** `UNASKED`, `ORDER BY md.wanted DESC` (`media/schedule.rs:166-171`).
  - **Measured (A3):**
    1. 16 history photos' jobs are running with their downloads held.
    2. A photo arrives, and the window shows 32 more.
    3. Once downloads go on, 26 of the 32 were downloaded before the arrival's thumbnail was drawn, 2.6 s after.
    4. Oldest first (M22), none were, and it took 0.31 s.

  - **Fix:** take what arrived live ahead of windows' wants, oldest first among themselves. That needs a `live` column on `media` and a partial index, and migration 13 can still change. Or draw an arrival's thumbnail outside the cap. Windows' wants can stay newest first.

/// Holds every one of jaw.db's readers until the sender is dropped.
fn hold_readers(rig: &Rig) -> crossbeam_channel::Sender<()> {
    let (gate, waiting) = crossbeam_channel::bounded::<()>(0);
    for _ in 0..8 {
        let (waiting, reads) = (waiting.clone(), rig.store.reads().clone());
        tokio::spawn(async move {
            reads
                .query(Priority::Interactive, move |_| {
                    let _ = waiting.recv();
                    Ok(())
                })
                .await
        });
    }
    gate
}

impl Rig {
    /// As hold_background, again: padding of its own, so it writes new frames.
    async fn hold_background_again(&self, round: &str) -> Connection {
        let reader = Connection::open(self.home.path().join("jaw.db")).unwrap();
        reader.execute_batch("BEGIN").unwrap();
        let _: i64 = reader.query_row("SELECT count(*) FROM messages", [], |r| r.get(0)).unwrap();
        let padding = (0..1_000)
            .map(|n| Change::Remember { key: format!("padding {round} {n}"), value: round.repeat(4_000 / round.len()) });
        self.store.apply(Lane::Live, padding.collect()).await.unwrap();
        reader
    }
}

## P1: the barrier, the synced commit and acks

### A row never names a file a power cut could lose

**What each call promises.** From `man 2 fcntl` and `man 2 fsync` on this machine (macOS 26.6.2):
- **`fsync`** moves a file's modified data and attributes to the drive. The drive "may also re-order the data so that later writes may be present, while earlier writes are not."
- **`F_BARRIERFSYNC`** "does the same thing as fsync(2) then issues a barrier command to the drive. The barrier applies to I/O that have been flushed with fsync(2) on the same device before. These operations are guaranteed to be persisted before any other I/O that would follow the barrier." The page gives the pattern for it: "execute operations of phase one, then fsync(2) each FD and issue a single barrier. Finally execute operations of phase two." Then "no file can possibly get persisted with the effect of the second phase without the effect of the first one." It is "implemented on HFS and APFS" and "requires hardware support, which Apple SSDs are guaranteed to provide."
- **`F_FULLFSYNC`** "drains the entire queue of the device and acts as a barrier, data that had been fsync'd on the same device before is guaranteed to be persisted when this call returns."

**What a download does.** In jaw-engine (`engine/internal/wa/media.go:238-266`), and the same in the demo engine (`engine/demo.rs:520`), one file at a time:
1. The file's bytes go into its partial file.
2. `F_BARRIERFSYNC` on the partial file: the bytes are flushed and fenced.
3. The partial file is linked in under its name, and the partial name is removed.
4. `F_BARRIERFSYNC` on the folder: its new entry is flushed and fenced.
5. The engine answers `PLACED`. Only then does jawd write the row naming the file (`media/fetch.rs:127-142`), in a synced commit. SQLite appends the commit's WAL frames, then runs `F_FULLFSYNC` on the WAL. `commits_synced` has checked `synchronous=FULL` and `fullfsync=1` first (`store/mod.rs:152`, `:885`, `:1271`).

**So, on macOS:**
- **The name can't reach the disk without the bytes,** because of step 2's barrier.
- **The row's frames can't reach the disk before the name or the bytes,** because of step 4's barrier, since the frames are written after the engine answers. That holds at every instant, including while the commit's `F_FULLFSYNC` runs, when the drive may write the frames in any order. A power cut leaves either the row with its whole file under its name, or no row.
- **The file is durable no later than its row.** When the row's commit returns, its `F_FULLFSYNC` has persisted everything fsync'd before it on the device, the file's bytes and name included.
- **A file already at its name** (the engine's `EXISTS`, or jawd finding it at `fetch.rs:120`) was fenced by the download that put it there, before this row's frames were written, so the same holds.

**On Linux,** `barrierSync` is `fsync` (`engine/internal/wa/fsync_other.go:14`), and the demo engine's is `sync_all`. On ext4, XFS and btrfs that flushes the device's cache, so the file and its name are durable before the engine answers, before the row is even written.

**What it rests on.** The first two rested equally under the old full flushes:
- `fsync` on a folder flushes the entries made in it. The old `F_FULLFSYNC` on the folder rested on the same thing, since it too is "fsync(2) then" a flush.
- The drive must honour barriers. The probe in Measurements found `F_BARRIERFSYNC` accepted on a file and on a folder here, so the engine never falls back. On a drive without barriers the man page doesn't say what happens, and a call that succeeds orders nothing (H16).
- The barrier orders one device. The media folders sit in jaw's folder beside jaw.db, unless `media` is linked to another volume (H16).

### No ack before its own synced commit, and the waiting writes neither starve nor reorder acks

- **No ack goes early.** An inbox group's acks go only after its commit (`store/mod.rs:1131-1135`), which takes the waiting writes in with it (`:1228-1232`) and is refused if it would run unsynced (`:1271-1274`). A waiting write is answered only after the commit that made it, the inbox group's or `flush_soon`'s, which checks the same (`:885`).
- **They can't starve.** The writer commits them all once the first one's time is up. It checks at the top of its loop, as its idle timer, between background transactions and while background work waits for the WAL (`:812-813`, `:841`, `:1330`, `:1511`), and before a truncate (`:1411`). Indexing steps and background batches end within 3 ms, so a write waits its 100 ms and a few milliseconds at most.
- **They can't starve acks.** Each adds its statements to an inbox commit (a file's row is two short statements), or, when no message is arriving, costs one synced commit per 100 ms at most.
- **They don't reorder acks.** Inbox rows keep their order and are acked by group, and a durable live write still goes in the next group's commit.
- **What can move** is a waiting write against writes queued after it, which may commit first. Every merge rule it meets gives the same result in either order: since I1's trigger, a deletion before or after the file's row ends the same way. And a job doesn't move on until its own row is answered.
- **Except** when an inbox commit fails inside a waiting write (I5).

### Inconsistency

- **I3. On macOS the settle can note previews durable before they're on the disk.**
  - **Where:** `media/settle.rs:158-168`, with `push` at `:178-186`.
  - **What happens:**
    1. The settle sends each preview and thumbnail made since the last time to the drive with a plain `fsync`, then the folder.
    2. It notes `settled` through their numbers in a synced commit.
    3. On macOS `fsync` stops at the drive's cache and orders nothing. So the note's WAL frames can reach the disk before the previews do, from the moment SQLite writes them until the commit's `F_FULLFSYNC` returns.
    4. A power cut then leaves jaw.db saying previews are durable when some are missing or cut short.
  - **Why it matters:**
    - The next start trusts every preview numbered up to `settled` without looking (`store/files.rs:83-87`). Nothing looks again, since the read path no longer opens files, so such a preview is shown broken until eviction.
    - That's what the numbering exists to prevent, and what P1's change avoids for downloads with a barrier.
    - Durability once the commit returns is fine. It's the order before it that isn't.
  - **Fix:**
    - Use the man page's two-phase pattern: `fsync` each file as now, then one `F_BARRIERFSYNC` (on the folder, with `F_FULLFSYNC` where it fails) before the note is written. One `F_FULLFSYNC` before the note would also do, at one flush every 5 s. On Linux, `sync_data` already makes each file durable.
    - Skip only a file that isn't found (`:161`). One that can't be opened for another reason must stop the settle, not be passed.
    - Test it as T2 tests the engine: hooks for the push and the barrier, recording that every file's push and the barrier come before the note is applied.
- **I4. The start's check passes a broken preview it couldn't mend, which is then shown and settled for good.**
  - **Where:** `media/settle.rs:104-113`, and `:97-99`.
  - **What happens:**
    1. At a start, `check` mends a broken preview or thumbnail. Mending needs the file's claim, which a job holds while it downloads the file.
    2. After 600 tries 50 ms apart, 30 s, it gives up and goes on.
    3. `files.checked(through)` passes the row anyway, so the read path shows it.
    4. The next settle notes it settled, so no later start looks at it.
    The same happens if the commit forgetting it fails for 30 s. And if the blocking task that reads a page's files panics, `unwrap_or_else(|_| Vec::new())` passes the whole page unread.
  - **When:** a thumbnail drawn in the seconds before a power cut, whose file was still downloading, and whose download at the next start takes more than 30 s: a large video, or a slow link. Rare, and lasting.
  - **Reproduced** (scratch test S2, with mending's tries cut to 4 and the check held 1.5 s so that the restarted download holds the claim first): with the file downloading, the half-written thumbnail is shown (`whole_preview` false), `remade` is 0, and the settle notes it settled, 1 of 1.
  - **Fix:**
    - Pass a row only once it's whole or mended: keep trying a row a job holds, without giving up, and keep `checked` and `inner.checked` below it until then.
    - Or keep unmended hashes in a set that `trusted` refuses and the settle stops short of.
    - Treat a page whose look failed as not looked at.
    - Test: S2.
- **I5. A transient failure inside an inbox group's commit drops the durable writes waiting to share it.**
  - **Where:** `store/mod.rs:1228-1232`.
  - **What happens:**
    1. `store_inbox` drains the waiting writes into its transaction, and returns at the first error.
    2. When one of them fails with an error `write::transient` takes as passing (a full disk, an I/O error), that write and every one behind it in the drain are dropped. Their callers are told "jawd's writer has stopped", which it hasn't, and their changes are never made.
    3. The writes already taken are made again alone, as other shared writes are.
  - **Reproduced** with the store tests' own `FAIL_SHARED` hook, which fails a write as a full disk inside an inbox group's commit (scratch tests S1 and S1b):
    - with three writes waiting and the first failing, all three are answered "jawd's writer has stopped", and none is made;
    - with the failing one between the other two, the first is made again and answered, and the other two are dropped.
  - **Why it matters:** `apply_durable_soon` is offered as `apply_durable` that may wait, and `apply_durable` tries again on a transient error rather than drop the write. Today's two callers recover: a file whose row is dropped is named when its job tries again, and the settle's mark goes again 5 s later. But the design's rule is nothing in flight lost on `SQLITE_FULL`, and a failure quarantined or retried, never dropped.
  - **Fix:**
    - Best, drop `apply_durable_soon` (P1).
    - Otherwise move each waiting write into `shared` before making it, so the failure path makes it again alone like the rest. Test it with the hook, as above.

## What was asked, checked

### Files and rows

- **A row names only a whole, synced file.** The engine flushes the partial file, links it in and flushes the folder before it replies (`engine/internal/wa/media.go:218-245`). jawd writes `Placed` only after that reply (`crates/jawd/src/media/fetch.rs:92-98`). A file found already at its name is reused as the same content: only the engine puts a file there, and only whole. Previews are derived and checked on read (below).
- **A file is deleted only after a synced commit stops naming it.** The cleaner takes an exclusive claim on each file. It then drops the rows in one `apply_durable` commit and only afterwards removes the files (`crates/jawd/src/media/cache.rs:289-308`). Mending a broken preview forgets it in a synced commit before removing it. Both rules are tested: switching off the sync, or removing first, each fails two tests.
- **A kill at any point.** I killed the flood bench with kill -9 twice mid-flood, with 67 and 119 copies downloading. Neither time did any row name a missing file or one with a wrong hash. Each left partial files, plus one whole downloaded file and a few whole previews whose commits hadn't happened yet. A start of jawd on each folder removed the partials (6 and 10), swept one unnamed file and reused the rest, after which every file on disk was named and whole. The cache's counters matched its rows.
- **Content addressing.** One download serves every copy of a file. That is tested, and duplicates share the download lane's key. The exception is H1: a file's name carries an extension taken from the copy's type, so two copies of one file with different types can be downloaded twice in a narrow race.
- **Previews as derived files.** A preview or thumbnail is put in place without flushes. The read path checks it once a run (`jaw_media::whole_preview`) before a row carries it. One that's missing, empty or cut short reads as missing, and is forgotten in a synced commit, removed and made again. This is tested: making the check always pass fails the power-cut test. Its cost on the read path is P3.
- **Except I1:** a copy deleted while its file or thumbnail is being made can leave a cache row no copy names.

### Downloads

- **Hash checks, cancellation, progress.**
  - **Hashes:** whatsmeow checks the encrypted and plain hashes and the MAC, and the engine hashes the whole file again before placing it. A mismatch is never placed (tested).
  - **Cancel:** it stops the engine's download and leaves nothing (tested). A download shared with another copy is downloaded again for that copy.
  - **Progress:** the engine reports at most 4 times a second, and only through `try_send`, so it never blocks the engine link. jawd writes it at most every 250 ms and 1%.
- **Replays and out-of-order arrivals.**
  - **A copy arriving again** fills in only what was missing. Its hash and keys stay once known, so a replay changes nothing (tested; overwriting the hash fails the test).
  - **An HD copy arriving before its SD message** waits in `pending` and attaches when the SD message comes (tested). Replaying it changes nothing.
  - **Wants:** a want only moves later. A job settles only the want it took (tested; both guards fail their test when switched off). I2 is the one path that breaks this.
- **The phone's answer late, twice or never.** I checked the late and twice cases at the store, in a scratch test:
  - **A late upload** (after the copy was left expired) is still downloaded from the new path.
  - **The same answer twice** makes the copy wanted one more time, at most one extra job that finds nothing to do.
  - **A late "not found"** after an upload is ignored.
  - **An answer once the file is here** changes nothing.
  - **Never:** a phone that never answers leaves the copy expired after two minutes, saying why, and asking again works (tested). A start asks again for copies left waiting, since the restarted engine can't read the answer (untested, T4).

### Bounds and lanes

- **Bounded, and in `jawd status`:**
  - **Downloads:** 6 at a time, queue 1,000. **Images:** half the cores, queue 1,000. Both report their depth, waits and runs.
  - **Jobs in flight:** at most 256 copies.
  - **Engine events:** the "a window showed it" channel holds 1,024 and the progress channel 256, both with `try_send`. The engine keeps at most 4,096 retry keys, for an hour (tested).
  - **Reported:** the cache's files, bytes and limit, and copies wanted, downloading and waiting for the phone. Also files no copy names, partials and orphans removed at start, files evicted, previews remade, and why background downloads are paused.
  - **The WAL** stayed under its bound in a 400-photo flood: 12,350 frames at its peak, against 15,360.
- **Acks during a photo flood: P1.** Separately, every media step goes on the writer's live lane (P2).
- **The cache's 5 GB: P4.** It can sit above its limit by the size of the starred and unsent files it reaches first.
- **Never a starred or unsent file:** tested, and evicting starred files fails the test.

### The engine (`engine/internal/wa/`, `proto/engine/`)

- **Streaming:** it streams. whatsmeow downloads into the partial file and decrypts there, and the hash check reads through a 32 KB buffer, so a file never sits in memory.
- **Synced before answering:** yes, as above, but no Go test fails without the file's flush or the folder's (T2).
- **Concurrency:** each command runs on its own goroutine, so a long download doesn't hold up sends.
- **Files already there:** a file at the name is never written over (tested; replacing `Link` with `Rename` fails the test).
- **The phone's answer** is kept through the inbox, as a message is, before it's acknowledged.

## Findings

### Data loss

### Inconsistency

- **I1. A copy deleted while its file or thumbnail is being made can leave a cache row no copy names, kept for good.**
  - **Where:** `crates/jawd/src/store/write/media.rs:217` (`PLACED`), `:226` (`THUMBNAIL`) and `:223` (`PREVIEWS`, which then fills the row in). Also `schema.rs:797`: `media_unnamed` fires only when a copy goes.
  - **What happens:**
    1. A copy is deleted, for you or for everyone, while its download or thumbnail job runs. If no `media_files` row exists for its hash yet, the trigger queues nothing.
    2. Then the download's `Placed` inserts a row naming the file, and the job adds its previews.
    3. Nothing names that row, `media_drop` doesn't hold it, `status` doesn't count it as unnamed, and the start's sweep keeps it, since a row names it. It stays until eviction happens to reach it, by the time it was placed.
  - **When:** no row exists yet whenever no thumbnail has been drawn. That covers voice notes and audio, most documents, and a photo or video whose thumbnail job is still queued, as in a flood. A thumbnail drawn after the deletion leaks the same way.
  - **Why it matters:**
    - The rows say no copy has the file, yet it's kept and counted in the cache.
    - The protocol says a message deleted for you or for everyone takes its file with it.
    - A revoked photo or voice note stays readable on disk, which is what "delete for everyone" asks jaw not to keep.
    - A photo sent to the wrong chat and deleted at once is a common case.
  - **Reproduced:** a scratch test gated a photo with no thumbnail at half its download, deleted its message (by revoke, and in a second test for you), let the download finish, and woke the cleaner for 3 s. Copies, `media_files`, `media_drop`, files and previews were `(0, 1, 0, 1, 2)`: 51,099 bytes kept, and `unnamed` 0. With a thumbnail drawn before the deletion, the cleaner removed everything, `(0, 0, 0, 0, 0)`.
  - **Fix:** queue a row that no copy names as it's written. Migration 11 isn't merged, so its text may change (with a new hash in `migrations.lock`). For example:

    ```sql
    CREATE TRIGGER media_files_unnamed AFTER INSERT ON media_files
    WHEN NOT EXISTS (SELECT 1 FROM media WHERE sha256 = new.sha256) BEGIN
        INSERT OR IGNORE INTO media_drop (sha256) VALUES (new.sha256);
    END;
    ```

    The cleaner then drops it in a synced commit and removes the files, as for any other. Another way: write `Placed` and `Thumbnail` only when a copy names the hash, and have the job remove what it wrote while it holds its claim. Test it with the scenario above, failing without the fix.
- **I2. A fold can give the kept copy a want that a job already took, so an interface's later `media.fetch` is dropped.**
  - **Where:** `crates/jawd/src/store/write/media.rs:277`: `wanted = coalesce(min(wanted, excluded.wanted), …)`.
  - **What happens:**
    1. A job takes the kept copy at want W, and an interface then asks for it, giving W+1, asked.
    2. The other copy (the same message in the LID or number chat being merged) had been wanted at W too.
    3. The fold takes the smaller, W, and keeps `asked`. When the job that took W settles, it clears the want and `asked`.
    4. If that job wasn't downloading (a video above the size set, shown in a window), the file is never fetched. Yet `media.fetch` had answered, synced, "so it's fetched however jawd stops".
  - **When:** it needs the two copies' wants to fall in the same millisecond, so it's rare. It's the class `13f6432` fixed for the other paths.
  - **Reproduced at the store:** after the fold, (wanted, asked) was (W, 1); after the job that took W settled, (None, 0).
  - **Fix:** as the other paths do, give the kept copy a want later than any a job took when the fold changes it, for example `CASE WHEN wanted IS NULL THEN excluded.wanted WHEN excluded.wanted IS NULL THEN wanted ELSE max(wanted, excluded.wanted) + 1 END`. Test: the scenario above.

### Unpredictable performance

- **P1. Downloads running back to back delay acks during a flood** (budget: 10 ms p99 for a message durable and acknowledged).
  - **Measured:** texts every 20 ms from one chat while photos poured into another, timing each text's ack during the photos' download phase.
    - **Texts alone:** 11.6 to 27.8 ms p99 in six runs at load 52 to 62. This machine's load already breaks the budget.
    - **Photos with their thumbnails and previews between downloads:** 15.7 to 18.5 ms p99 in three of four runs, and 79 ms in one.
    - **Downloads back to back** (image work switched off, as a flood of voice notes or documents runs): 35 and 59 ms p99 (maxima 97 and 187 ms) on the live lane, and 52 and 19 ms with the media steps moved to the background lane.
  - **Cause:** most likely the drive. Each downloaded file's `F_FULLFSYNC` (one at a time in jaw-engine, back to back across six download workers) occupies it, and each ack's synced commit waits behind it.
    - The writer's queue doesn't explain it: with the media steps on the background lane, one of the two such runs still had a 52 ms p99.
    - Runs at this load vary widely, so re-measure on a quiet machine.
  - **Decide before landing:** either the owner accepts slower acks during floods (J7's open question), or the flushes are paced. Options:
    - one `F_FULLFSYNC` for a group of files;
    - `F_BARRIERFSYNC` on each file, which orders its data before every later write, including the commit that will name it, leaving durability to the next synced commit's full flush;
    - holding background finishes while acks wait.
- **P2. Every media step goes on the writer's live lane.**
  - **Where:** `crates/jawd/src/media/schedule.rs:215` and the other `Lane::Live` calls in `schedule.rs`, `fetch.rs`, `previews.rs` and `save.rs`. The design puts auto-downloads, off-screen previews and media retry on the background lane.
  - **Measured:**
    - In floods, media steps are most of the live writes, and the writer's live-write wait p99 was 6.4 to 6.6 ms in three runs, against 0.9 to 1.0 ms with the job steps on the background lane.
    - In one flood, 673 of them rode inside the inbox's synced commits; on the background lane, none did.
    - Texts' acks and their time to an interface didn't differ measurably between the lanes, within this machine's noise.
  - **Fix:** may stand as a follow-up. Put the jobs' steps on the background lane, which also subjects them to the WAL bound. Keep what an interface asks for (`media.fetch`, `media.cancel`, `media.save`'s want) live and synced.
- **P3. The first read of a page of photos after a start checks every preview and thumbnail on disk, on the reader** (budget: a 100-message page in 5 ms).
  - **Where:** `crates/jawd/src/store/read.rs:438` and `crates/jawd/src/store/files.rs:72`.
  - **Measured:** a 100-photo page, 300 derived files, in a debug jawd with optimised dependencies at load 57. Cold took 17.3 ms p50 (25.0 ms max); warm, 2.8 ms. The checks alone (open, fstat, two reads, close) cost 12.5 ms for 300 files, and one run stalled for 4.8 s under this machine's I/O.
  - **Effect:** each page of photos pays this the first time it's read in a run. It's still within the 30 ms for opening a chat.
  - **Options:** only a power cut can break a derived preview, so check only after an unclean stop, or only files written since the last clean one. Or check off the read path and push a correction.
- **P4. The cache can sit above its limit by the size of the starred, unsent or claimed files it reaches first.**
  - **Where:** `crates/jawd/src/media/cache.rs:251-277`. The cleaner subtracts each candidate's size from what it must free before the drop has decided whether it may go. When the files used longest ago are starred, `over` is used up on files that stay, and the files after them are never reached.
  - **Measured:** limit 400,000 bytes, four starred photos of 383,332 bytes, then 24 small ones. The cache settled at 714,371 bytes in 15 files, with 13 evicted and 331,039 bytes unstarred. Unstarred files stay at about nine tenths of the limit plus whatever the starred ones take.
  - **Fix:** may stand as a follow-up, though it's small. Count only what the drop actually removed, and go on past files it kept.
- **P5. `media.save` waits for a download inside the connection's loop.**
  - **Where:** `crates/jawd/src/sock.rs:99` awaits `answer` inline. `media.save` waits up to `WAIT`, 600 s (`crates/jawd/src/media/save.rs:21`, `:71`), and copies the file before it replies.
  - **What happens:** meanwhile that connection reads no request, answers nothing, and sends no push or window update. An interface that saves a file not downloaded yet stops updating for up to 10 minutes. That breaks principle 1, and for that interface the 5 ms budget for a message reaching it. After sock-flood, pushes and windows go on, but every later request on the connection, `send.text` included, waits behind it.
  - **Fix:** must change. Answer `media.save` on a task of its own, as `find` is, on either version of `sock.rs`.

### Hygiene (follow-ups; none blocks)

- **H1. A file's name carries an extension** from the copy's type or name (`crates/jawd/src/media/fetch.rs:50-71`).
  - **The race:** two copies of one file with different types get different names. A job that read the copy before the other's `Placed` commit, and submits after that download ended, downloads the file again under its own name.
  - **The result:** a second download, and a file no row names until the next start's sweep.
  - **Fix:** name the file by its hash alone, or look for any name with the hash before downloading.
- **H2. `used_at` misses views and asks.** It's refreshed when a file is placed, previewed or saved. It isn't refreshed when a window shows the file, or when `media.fetch` asks for one already here (the only `Step::Used` is in `save.rs:51`). So eviction drops what was placed longest ago, not what was opened longest ago, as the design, the protocol and the schema's comment say.
- **H3. Three status counts aren't pinned.** `status` counts wanted copies, copies waiting for the phone and unnamed files through `Store::count`, with SQL passed as a table name (`crates/jawd/src/media/mod.rs:211-214`). The plan test never sees them. Their plans are bounded (a search of `media_wanted`, a scan of the partial `media_waiting`, a scan of `media_drop`), and each opens a connection of its own, four per `status`.
- **H4. `media.save` takes no claim and can leave a partial.** It copies out of the cache without a claim, so an eviction meanwhile fails the save; nothing is lost. Its hidden partial in the user's folder (`.<name>.<pid>-<n>.part`, `save.rs:127`) is left there for good after a crash.
- **H5. An HD copy gone from the server can't be asked for again.** It says "ask for it to have your phone send it again", but jawd never asks the phone for an HD copy (`fetch.rs:193`), so asking again settles it the same way.
- **H6. A cache file deleted from outside jaw leaves its copy `local` for good.** A job takes `copy.local` without checking the file is there (`schedule.rs:290`).
- **H7. `media`'s class undersells it.** An HD copy's keys live only in `media`, since the HD message isn't kept as a row, so no rebuild from raw can bring an HD copy back. Say in the class that every rebuild copies the table, or keep the HD message's raw.
- **H8. A clock set back delays "the phone didn't answer".** `retried_at` is wall-clock time, so with the clock set back, a copy waiting for the phone waits as long as the jump (until a restart) before it's said to be unanswered. Clamp it, as the data review's H8 asks for stored times.
- **H9. Some CHECKs list values that will grow.** The CHECKs on `media.state`, `variant` and `keys` enumerate values. The data review (I8) keeps CHECKs to invariants that never change, since adding a state later means rebuilding `media`, then a data step.
- **H10. A `jaw-client` test flaked once.** `an_interface_that_falls_behind_is_told_to_watch_again_and_ends_as_a_fresh_one` failed once in four runs at load 52 to 60, on a time limit, and passed three reruns. The demo account now includes a photo, which adds downloads and drawing to tests that use it.
- **H11. Nothing in jaw.db says a file was opened.** That's H2's root, and it shapes the library to come: it may want an `opened_at` of its own.
