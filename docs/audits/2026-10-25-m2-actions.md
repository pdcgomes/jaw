- **H20. Migration 10's kind, and the cost written beside it.**
  - **What's written** (`store/schema.rs:679`): "a data step ... its time doesn't grow with the messages: 2.7 ms ... its commit included".
  - **What it costs as run:** a data step runs alone and checks every foreign key in the database before it commits (`store/schema.rs:877`). Measured through the runner, on files at version 9 with a full outbox of failed rows that it removes:
    - beside 200,000 messages (141 MB): its `DELETE` 2.1 ms, the foreign-key check 130 ms, the step 170 ms in all;
    - beside 1,000,000 (696 MB): 2.2 ms, 637 ms and 665 ms.
  - **Before it,** a data step needs a synced backup, and free space of three times jaw.db or jawd refuses to start (`store/schema.rs:861`, `:934`).
    - From version 1 to 5 one is taken anyway, for migrations 3 and 6.
    - From version 6 to 9, main's jaw.dbs among them, migration 10 alone takes one: 0.72 s at 141 MB and 3.7 s at 696 MB.
  - **By the design's definitions it's a schema step:** it costs the same however big the database is, and it drops or rebuilds no table that others refer to. The foreign-key check buys nothing here, since nothing refers to the outbox.
  - **Fix, before merge while it can still change:** declare it `schema`, which it is by cost, or keep `data` for the backup and write what it costs as run, the foreign-key check included, as migration 6's note does.
  - **Either is safe, as checked here:** as a schema step it can't leave a row referring to nothing, and the fault test covers it in whichever transaction it runs; as a data step it's within budget. Neither needs another audit.
- **H21. A full outbox of messages WhatsApp refuses for good can't be emptied.**

- **H22. A reaction held on a message deleted for everyone is sent, kept on the deleted row and shown.**

  - An edit then changes nothing, since an edit never changes a deleted row (`store/write.rs:1845`). But a reaction is kept on it (`:1831`), and windows show a row's reactions whether or not it's deleted (`store/read.rs:337`). The phones show none on a deleted message.

### Inconsistency

**I5. A failed message of yours that nothing can send again stays in the outbox for good.** This is the builder's first note for the owner, plus three more ways to the same state that this branch opens.
- **What a failed row means:** the schema's "failed: waiting for send.retry", counted toward the thousand and in error 5's `failed`.
  - Queued and unconfirmed rows always come to an end, by an answer, a refusal or their day's timer, and each end drops a row whose message has gone (`dropped`, `store/write/outbox.rs:717`).
  - A failed row ends only through `send.retry`.
- **The four ways**, each a scratch test on the demo engine:
  1. **Deleted for you once it had failed.**
     - `delete_row` (`store/write.rs:953`) removes the message and leaves its outbox row, whose `message` goes NULL.
     - `send.retry` can't reach that row: the writer's `retry` (`store/write/outbox.rs:845`) finds no message, and the call answers `{}` without sending anything (`send/outbox.rs:527`).
     - Measured: the outbox kept one failed text row with no message, and counted it toward the thousand, as 1 waiting and 1 failed.
     - On main this needs your phone's app state to delete for you a message jaw has as failed, which the phone has only if WhatsApp did take it: rare. Here it's jaw's own `delete` for you, which is how you'd clear a failed message.
  2. **Deleted for everyone from another device, or by history, once it had failed.**
     - Only jawd's own deletion cancels its message's row (`acted`, `store/write/outbox.rs:546`). `apply_amendment`'s revoke (`store/write.rs:1846`), which revokes from other devices and history's revoke stubs go through, doesn't.
     - The row stays failed, and `RETRYABLE` (`store/write/outbox.rs:230`) now refuses it for good, since a deletion is sticky. Before this branch `send.retry` would have sent it again (the first audit's I2); now nothing can.
     - Measured: one failed text row, counted as 1 waiting and 1 failed; `send.retry` answered error 4.
     - The builder's own test does exactly this, in the second half of `a_deletion_for_everyone_of_a_message_whatsapp_refuses_leaves_nothing_of_it_to_send_again`, and checks only the error.
  3. **The same while it was unconfirmed,** and then no receipt in its day: `no_receipt` fails it, and it stays as in 2. Measured the same.
  4. **Your own deletion for everyone, kept for a late receipt.**
     - `RETRYABLE` refuses a message while a deletion of it is in the outbox, and a kept one stays until it's pruned.
     - Pruning happens only when another action is kept (`:818`). With none, it stays for as long as jaw runs.
     - Scene: a message on its way when jawd stopped, its deletion queued behind it, both refused once it started, when they may have gone, and no receipts.
     - Measured: the outbox kept a failed text row and a failed revoke, and counted 1 waiting and 1 failed. `send.retry` said "it was deleted for everyone, so it isn't sent again", while the row showed the message failed and not deleted.
- **Why it matters:**
  - Each such row holds a place in the thousand, and in `failed`, for good, and the count isn't one any window shows. In the first way, no window has the message at all.
  - Enough of them stop all sending with error 5, and nothing a user can do frees them: `send.retry` can't, and a deletion for you is refused once the outbox is full (`store/write/outbox.rs:479`).
  - `send.retry` answers success in the first way and error 4 in the other three. The README says error 3 "once nothing of it is left" (`protocol/README.md:312`), and that a failed message deleted for you has "nothing left to retry" (`:206`).
- **Fix:** keep one invariant in the writer: *every failed outbox row of a message can be retried.* Wherever a row fails, or its message stops being retryable, a failed row that `send.retry` would refuse goes in the same transaction. The message's own row still shows it failed.
  - In `delete_row`, from jaw or from app state, drop the message's row if it's failed. A queued one still goes, as on the phone, and an unconfirmed one ends at its timer.
  - In `apply_amendment`'s revoke of a message of yours, wherever it comes from, cancel its unconfirmed or failed row, as `acted` does now.
  - When `no_receipt` keeps a deletion for everyone, cancel its message's failed row. When `no_receipt` fails a message whose deletion is kept, drop its row rather than leave it failed.
  - Then `send.retry` answers 3 in each way, as the README says.

  Rows an earlier run left this way need the same once, at start. The outbox is small, so that costs nothing.
- **Test:** each of the four ways ends with no failed row that `send.retry` refuses or can't find, and `send.retry` answers 3. My scratch tests set each up: `audit_a_failed_message_*`, `audit_an_unconfirmed_message_*` and the "audit revoke behind" scene, in `/tmp/jaw-m2-audit2-s/crates/jawd/src/send/tests.rs`.

## In short

Changes needed.

The core is sound:
- **Durable before answered.** Each action is one synced commit before it answers, tested for all five with the synced-commit counter. Its own ID gets a tombstone in that commit, so receipts for it never wait in `pending`.
- **Done only once WhatsApp has it.** An action changes its message's row only once WhatsApp has it, by its answer or by a receipt for its ID, through the same `apply_amendment` rules every amendment follows:
  - an edit wins by its time and never changes a deleted row;
  - a reaction wins by its time;
  - a deletion is sticky.
  
  A refusal leaves the row as it was and tells every interface.
- **Merges.** Actions follow their message through a merge: `FOLD_TARGETS` moves them, and `fold` carries a revoke, edits and reactions onto the kept copy. Tombstones move at `start_merge`, and actions find their message through `located`.
- **The read position.** Reacting, editing and deleting for everyone leave the read position, unread and "told" as they were (scratch test).
- **Schema and plans.** Migration 9 is a sound schema step, and every new statement's plan is pinned.
- **The first run.** The first run on a version-1 database is unaffected.

These need fixing before it lands:
- Four inconsistencies:
  - **I1.** `forward` reads every chat it goes to, and sends read receipts there.
  - **I2.** An edit or deletion for everyone of a message of yours that hasn't reached WhatsApp goes even when that message is refused. `send.retry` then sends the original, so the recipients and jaw disagree.
  - **I3.** `forward` and a reply's quote send an edited message's text from before the edit.
  - **I4.** A receipt that comes after an action's unconfirmed day can't apply it.
- Missing tests: three rules have no test that fails without them (T1 to T3), and one test is flaky (T4).

## Findings

### Data loss

None.

### Inconsistency

**I1. `forward` reads every chat it forwards to, and tells WhatsApp so.**
- **Where:**
  - `send/forward.rs:133` calls `reads::want` for each chat.
  - `store/write/outbox.rs:584` (`enqueue_one`) writes each forwarded message with `here: true`.
  - `store/write.rs:1688` and `settle_each` (`:755`, `:758`) take that as reading the chat. The position moves to the forwarded message, and "told" is frozen before it, so receipts are owed for every message it passes over.
- **What happens** (scratch test): Rui's chat had 2 unread messages and no read position. I forwarded one of Ana's messages to it. Afterwards:
  - its unread was 0, and its read position was at the forwarded message;
  - the engine was asked `MarkRead` for both of Rui's messages. That sends blue ticks for messages nobody opened in jaw.
  
  Read receipts can't be taken back, and a forward goes to up to five chats at once.
- **Why it's wrong:**
  - The README says sending a message reads the chat "as replying on the phone does", which happens from inside the chat. A forward is chosen from a list of chats and is a reply in none of them, and the README doesn't say it reads them.
  - This branch's brief is that your own actions leave the read position and unread as they were. Reacting, editing and deleting do (scratch test).
- **Fix:** forwarded messages don't read their chats.
  - Write them so they neither move the read position nor freeze "told": neither the `here` path nor the other-device `mine` path, with a flag on `Message`, say.
  - Drop the `reads::want` call.
  
  If the owner wants a forward to read its chats, say so in the README instead, with a test.
- **Test:** forwarding into a chat with unread messages leaves its unread, position and "told" as they were, and the engine is asked no `MarkRead`.

**I2. An action on a message of yours that hasn't reached WhatsApp goes even when that message is refused, and `send.retry` then undoes it for the recipients.**
- **Where:**
  - `edit` and `delete` for everyone refuse only a message whose status is `failed` (`send/actions.rs:280`, `:336`), so a `pending` one is taken. `react` doesn't look at the status.
  - The action is queued behind its message in the chat's queue. A refusal of the message ends that message's job (`send/outbox.rs:358-364`), so the action goes next.
  - `send.retry` (`send/outbox.rs:405`) sends the message's own raw again, whether or not its row was edited or deleted since.
- **What happens** (two scratch tests, demo engine, WhatsApp unreachable at first): a message "hi" waits, and an edit to "hello" is taken. WhatsApp then refuses the message and takes the edit, which is done to the row. `send.retry` then sends "hi" again.
  - WhatsApp was sent `"hi"` (refused), the edit, then `"hi"`. jaw shows "hello", sent.
  - With a deletion for everyone instead of the edit, jaw shows "You deleted this message", sent. The recipients' last copy is "hi", which arrived after the deletion. `send.retry` answered success for the deleted message.
- **How it's reached:**
  - By a refusal specific to the message (one the server won't take) rather than to the chat. An action to a chat that refuses everything is refused too, and its message's row stays as it was.
  - By a message left unconfirmed that fails after its day.
  - With no refusal at all, during a merge. The action is queued under the kept chat's JID and its message under the gone chat's, so the action can go first. That's the send audit's H13, which actions now make an inconsistency.
- **Fix:**
  - An action on a message of yours waits until that message has reached the server. Either refuse it (error 4, "it hasn't gone yet") while the message is `pending`, or hold it in the queue until its message is sent and refuse it if its message fails.
  - `send.retry` refuses a message deleted for everyone.
- **Tests:** the two scenarios above end with jaw and what WhatsApp was sent agreeing, and a merge can't send an action before its message.

**I3. `forward` and a reply's quote send an edited message as it was before the edit.**
- **Where:** both build what they send from the row's `raw` (`send/forward.rs:54-61`, `send/quote.rs:57-61`). An edit changes a row's `text`, `spans` and `summary`, never its `raw` (`store/write.rs:1827`).
- **What happens** (scratch test): Ana sent "chego às 20h" and then edited it to "chego às 21h", which jaw shows.
  - Forwarding it sent "chego às 20h".
  - Replying to it quoted "chego às 20h".
  
  jaw's new rows are converted from what was sent, so jaw's own forward and quote say 20h too.
- **Fix:** when the row has `edited_at`, take what the message says from the row: its `text` for a text message, and its caption once caption edits are kept.
- **Test:** forwarding and replying to an edited message send its edited text.

**I4. A receipt that comes after an action's unconfirmed day can't apply it.** This is one of the builder's notes.
- **Where:**
  - `no_receipt` drops an action's outbox row, and its effect with it (`store/write/outbox.rs:773-779`, through `acted(…, false)`), and every interface is told WhatsApp refused it.
  - `receipt_for_action` (`:529`) looks only in the outbox, so a receipt for that ID that comes later finds nothing.
- **What happens:** take a reaction that jawd sent again after a restart or a failed attempt, which WhatsApp refused, and which had no receipt for a day, for example because the recipient's phone was off for two days. That phone comes back and sends its receipt: WhatsApp has the reaction and the recipient shows it. jaw never will, and it has told you WhatsApp refused it.
- **Why it matters:** messages don't have this hole. The README says any receipt settles a message, and a late one moves a failed message on. An action's effect is gone with its row, so a late receipt can't do the same.
- **Fix:** keep the effect of an action dropped this way where a receipt for its ID can still find it, and apply the effect if one comes. For example, leave the row as `failed`: not shown in windows, outside the thousand, not retryable, and pruned after a long while such as 30 days.
- **Test:** a receipt after the day applies the action and tells windows.

### Hygiene (follow-ups; none blocks)

- **H1. Clocks.** Your own actions are stamped with the Mac's clock, reactions with their sender's, and both win by their time.
  - So your newest action from jaw can lose to an older one from a phone whose clock runs ahead, or to an earlier one of your own after the Mac's clock goes back.
  - When it loses, the call still answers success, the overlay hides it (`mine_at`), and the row keeps the older one.
  
  Consider stamping your own action at least a millisecond after whatever it replaces on the row, and sending WhatsApp that same time.
- **H2. A reaction's removal leaves nothing behind** (`DELETE FROM reactions … at <= ?3`, `store/write.rs:1810`), so an older reaction applied after a newer removal comes back.
  - This is main's rule. But jawd's own reactions are now applied late by design (at `Sent`), which makes it easier to reach: you react in jaw while offline, then remove a reaction from your phone.
  
  Keep a removal as a row with its time, and filter it out where reactions are read.
- **H3. Tombstones gain one row for every action**, yours here and those from your other devices, for as long as the account is linked. That's about 40 bytes each, and `jawd status` doesn't count them. Report the count.
- **H4. `Amendment`'s JSON is now persisted in `outbox.effect`** as well as in `pending.effect`, and `action()` fails on one it can't read. A serde change in a later jawd would quarantine every `Sent` for a queued action, and send that action again at each start. Pin each variant's JSON in a test.
- **H5. One effect that won't decode hides all of a message's pending actions in windows.** `overlay::pending` returns nothing for the whole array (`store/overlay.rs:36-41`). This affects display only.
- **H6. jaw sends neither `key` nor `chat` with its actions** (`crates/jaw/src/wire.rs:597-618`). jaw knows both, so it should send them:
  - jaw reports a lost answer rather than resending it, but a manual retry of a `forward` sends its messages twice. That's N7 again, for actions.
  - Every action looks for its message in each chat.
- **H7. A deletion for you asked again without a key is error 3** (`find`, on the read pool), not done, although the message is gone as asked.
- **H8. A message deleted for everyone keeps its media rows and files until M3**, as the builder says, but the README says they're dropped from the cache. Say "from M3" there until then.
- **H9. `own_action`'s tombstone can make an empty chat.** When your phone reacts, edits or deletes in a chat jaw doesn't have yet, it creates a chat row (`ensure_chat`, `store/write.rs:1749`), and the chat list shows empty chats. That's rare once history has arrived.
- **H10. A group member who left before receiving drops off `message.info`** once the message settles. This is one of the builder's notes, and it can stand.
- **H11. Two schema hardenings:**
  - a `CHECK` that a row has an `effect` exactly when it's a reaction, edit or revoke;
  - a `CHECK` on the values of `outbox.kind`.
- **H12. A deletion for everyone asked twice, before WhatsApp has the first, sends two deletions.** This is one of the builder's notes, and it's harmless, since a deletion is sticky everywhere.

### The rest, checked

- **Durability.** `react`, `edit`, both deletions and `forward` each make exactly one synced commit before they answer; `message.info` and `chat.info` make none (`each_sending_call_that_keeps_something_is_one_synced_commit`).
  - A deletion for you commits the row's removal, its tombstone and the app-state row together.
  - A forward commits all of its messages and outbox rows, or none of them.
  - `Sent` and refusals go through `settle`'s retry loop at `NORMAL`. If that commit is lost, the row is sent again with its ID.
  - A restart sends a queued action again with its ID (tested).
  - An app-state patch sent twice sets the same thing twice.
- **Keys and repeats.** Keys are checked inside each step's transaction as well as on the read pool. Without a key:
  - `react` with the same emoji, or `edit` with the same text, asked again sends WhatsApp a second message, and the row ends the same;
  - a deletion for everyone asked twice sends two, and a deletion is sticky;
  - a deletion for you asked again is error 3 (H7);
  - a `forward` asked again sends its messages again (H6).
- **Your other devices.**
  - Your own reactions from your phone are filed under the same JID as jawd's (`Me::jid`, `my_jid`), so the two share a row.
  - The by-time rules hold whichever arrives first. That's tested for a reaction and an edit from your phone that were later but arrived first.
  - A deletion from anywhere is sticky against edits and against the overlay.
- **Out of order.**
  - jawd's own actions need their message, which `located` finds after moving it out of a chat being merged.
  - Amendments from others, and from your phone, that arrive before their message wait in `pending` as before.
  - The IDs of actions from your other devices get tombstones, so receipts for them don't wait.
- **Merges.**
  - Tombstones move to the kept chat at `start_merge`, so a receipt for an action's ID finds it under either JID.
  - `folded` moves actions to the kept copy, and `fold` carries a revoke, edits and reactions onto it (tested).
- **The read position.** Reacting, editing and deleting for everyone leave the position, unread and "told" as they were (scratch test). A deletion for you recounts unread from the same position, as derivation should.
- **Plans.** Every new statement is pinned, in `plans.txt`, in `outbox.rs`'s plan test or in `send/tests.rs`'s.
  - The windows' new subqueries are index searches of `outbox_by_target`, and so is the cascade from `messages` to `outbox.target`.
  - The one new scan, an action named without its chat looking in each chat, is allowed.
  - The reactions subquery's temporary b-trees are main's, allowed for one message's reactions; the plan test sees them now.
- **Migration 9.**
  - **What it does:** it adds two nullable columns and two indexes to `outbox`, which holds at most 1,000 rows, so it costs the same however big the database is. Nothing is dropped.
  - **Constraints:** the new `CHECK` reads each existing row once, and `ON DELETE SET NULL` has its index.
  - **Declared:** the class is declared as jaw's own, and it has a `migrations.lock` line of its own.
  - **Its tests pass:** every earlier version upgrades with its rows kept, a fault at any statement leaves the database as it was, and the fingerprint matches.
- **The engine.**
  - `AppStatePatch` is validated before it's sent.
  - whatsmeow at the pinned version retries a 409 conflict itself, and the engine retries other errors while connected, so a passing conflict doesn't drop a patch.
  - Nothing in `session.db` changes beyond whatsmeow's own app-state store.
- **History.** A revoke stub becomes a deletion plus a deleted row with its raw.
  - A copy jaw already has loses its content.
  - No later copy can bring it back, since a deleted row is never upserted again (`store/write.rs:1573`).
  - Every history row is still either a message with its raw or kept whole in `history_kept`.
