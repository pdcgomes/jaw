    SELECT m.deleted
        OR EXISTS (SELECT 1 FROM outbox a WHERE a.target = m.n AND a.kind = 'revoke' AND a.state <> 'failed')
        OR EXISTS (SELECT 1 FROM chat_merges cm JOIN messages g ON g.chat = cm.gone AND g.id = m.id

    /// everyone commits and reaches `state`: what the step answers, and the outbox after.
    async fn reaction_stopped_while_your_deletion_is(state: &str) -> (Result<Value, Error>, Vec<(String, String)>) {
        let home = tempfile::tempdir().unwrap();
        let timing = Timing { unconfirmed_for: Duration::from_secs(1), ..quick() };
        let running = Running::timed(home.path(), world(), true, true, timing).await;
        running.chats(&[ANA]).await;
        let id = running.send(ANA, "chego às 20h").await;
        running.until_status(ANA, &id, "sent").await;
        let (stopped, go) = running.sending.pause_next_action();
        let sending = running.sending.clone();
        let params = json!({ "message": id, "chat": ANA, "emoji": "👍" });
        let asking = tokio::spawn(async move { sending.call("react", params).await });
        stopped.notified().await;
        let revoke_is = |state: &'static str| {
            move |db: &Connection| {
                let now: Option<String> =
                    db.query_row("SELECT state FROM outbox WHERE kind = 'revoke'", [], |r| r.get(0)).optional()?;
                Ok(now.as_deref() == Some(state))
            }
        };
        let delete = || running.call("delete", json!({ "message": id, "chat": ANA, "for": "everyone" }));
        match state {
            "queued" => {
                until_offline(&running).await;
                delete().await.unwrap();
            }
            "handed to the engine" => {
                running.world.hold(true);
                delete().await.unwrap();
                running.world.until(|asked| asked.iter().filter(|k| matches!(k, pb::command::Kind::Send(_))).count() >= 2).await;
            }
            "waiting for a receipt" | "kept for a late receipt" => {
                // The first try fails on the way, and the next is refused when it may have gone.
                running.world.fail_chats(&[ANA.to_string()]);
                delete().await.unwrap();
                running.world.until(|asked| asked.iter().filter(|k| matches!(k, pb::command::Kind::Send(_))).count() >= 2).await;
                running.world.refuse_next(1);
                running.world.stop_failing_chats();
                eventually(&running, "the deletion waiting for a receipt", revoke_is("unconfirmed")).await;
                if state == "kept for a late receipt" {
                    eventually(&running, "the deletion kept for a late receipt", revoke_is("failed")).await;
                }
            }
            "done" => {
                delete().await.unwrap();
                until_stored(&running).await;
            }
            "refused" => {
                running.world.refuse_next(1);
                delete().await.unwrap();
                until_stored(&running).await;
            }
            other => panic!("no state {other}"),
        }
        go.notify_one();
        let answered = asking.await.unwrap();
        (answered, outbox_rows(&running).await.0)
    }

    #[tokio::test(flavor = "multi_thread")]
    async fn the_step_refuses_a_reaction_in_each_state_of_your_deletion_for_everyone_that_windows_show_as_deleted() {

                Ok(_) => assert!(!refused && written, "{state}: taken, {rows:?}"),
            }
        }
    }

### H33: what gets past it, and a kill at each step

- **A window between the check and the step (H36).** `react` and `edit` read `deleting` on a reader (`send/actions.rs:245`, `:280`). The writer's step (`act`, `store/write/outbox.rs:458`) then writes the action without checking again, aimed at the copy of the message it finds (`located`, `store/write.rs:1450`). - **A kill can't leave anything of the check.** It reads and writes nothing:

- **H30 is closed in the order it was found, from every source.** A reaction or an edit still to go, whose message is deleted for everyone and then for you, is withdrawn once, with one notice, and nothing of it is sent. That holds whoever deletes it for everyone and wherever the deletion for you comes from, and through replays, duplicates and a kill between the two commits. The mark is set in the deletion for you's own transaction, before the message's row goes, and nothing ever clears it. Each of the builder's two tests fails with the mark not set, and with it not read.
- **The condition that keeps the mark off is untested (T1).** With the mark set on every action of a message deleted for you, deleted for everyone or not, the whole suite passes. A reaction to a message you only deleted for you is then not sent, and you're told it was deleted for everyone.
- **Migration 12 is a correct schema step.** It adds one column with a constant default to the outbox, one of jaw's own tables, which holds at most 2,000 rows. Through jawd's runner it took 27 ms at a million messages and 31 ms at 200,000. It writes two pages and keeps every outbox row as it was, each with 0.
- **H24 is closed.** Every message row is built in one place, which now leaves out a deleted row's reactions once your actions on their way are shown over it. No SQL changed. It hides reactions only on rows shown deleted: when WhatsApp refuses your deletion for everyone, they're shown again.

## What was asked, checked

### Migration 12

- **A schema step, declared.** `ALTER TABLE outbox ADD COLUMN target_deleted INTEGER NOT NULL DEFAULT 0 CHECK (target_deleted IN (0, 1))` (`store/schema.rs:723`) is a column with a constant default, which the design's "Migrations" names as a schema step. It declares its class ("jaw's own column on the outbox", `:718`) and has its line in `store/migrations.lock:27` (`12 schema a353…0710`). The frozen-text test passes. Main's 11 is the budgets index, so 12 is the next number today.
- **Safe on a full-size jaw.db.** `ADD COLUMN` rewrites only the table's line in `sqlite_schema`. The new `CHECK` is verified by a `quick_check` of the outbox alone, which holds at most 1,000 rows waiting and 1,000 actions kept for a late receipt. Measured through jawd's runner, the step took 31 ms on a 244 MB jaw.db of 200,000 messages and 27 ms on a 1,217 MB one of a million. The statement alone took 4.6 to 26 ms in both. The WAL afterwards held 8,272 bytes (two pages), and jaw.db's size didn't change.
- **Killed-safe.** It's one statement, run in the schema steps' single `BEGIN IMMEDIATE` transaction with `user_version` and the fingerprint check. A kill rolls it back, and the next start runs it again. The fault-at-every-statement test injects a failure at it from every earlier version, and passes.
- **An older outbox upgrades cleanly.** I built a jaw.db at version 11 with 2,002 outbox rows: failed messages of yours, queued, unconfirmed and kept reactions, an edit and a reaction already aimed at nothing, and app state. Taken to 12 by jawd's runner, every row was kept as it was, each with 0, `integrity_check(outbox)` said ok, `foreign_key_check` found nothing, and the version was 12. `a_database_at_every_earlier_version_keeps_its_rows` covers versions 1 to 11.
- **Rows from before take 0, which is right.** Nothing left in jaw.db says whether a message already deleted for you had been deleted for everyone: its row is gone, and its tombstone doesn't say. So the actions on those messages go, as they would have on main.

### `target_deleted`

- **Set in the deletion's own transaction, before the row goes.** `delete_row` (`store/write.rs:965`) calls `deleted_for_you` (`store/write/outbox.rs:904`), which runs `KEEP_DELETED` (`:240`). It then deletes the message, whose foreign key nulls the actions' `target`. Every deletion for you goes through `delete_row`:
  - jaw's `delete` (`store/write/outbox.rs:551`);
  - your phone's app state and history (`apply_amendment`, `store/write.rs:1835`);
  - `Change::DeleteMessage` (`:570`);
  - a merge's copy of a message already deleted for you in the chat kept (`:1395`).
- **No other path deletes a message an action is aimed at.** A merge's fold (`:1506`) first moves the gone copy's actions to the copy kept (`folded`, `store/write/outbox.rs:1284`), and makes a deletion for everyone stick there. A merge removes its gone chat only once all its messages have moved (`store/write.rs:1370`).
- **Read in one place.** `OUTBOXED` reads `coalesce(t.deleted, o.target_deleted)` (`store/write/outbox.rs:218`), so the message's own row says while it's there. Only `Outboxed::withdrawn` (`:1117`) reads the result, and only for a queued reaction or edit. An unconfirmed or kept action carries the mark inertly, since nothing queues those again.
- **Never cleared, and never stale.** No statement sets the column to 0, and a deletion for everyone is sticky: `upsert_message` leaves a deleted row alone (`store/write.rs:1600`). So an attempt's decision to withdraw can't become wrong between its read and its step, which only checks the row is still queued (`STILL_QUEUED`, `:414`).
- **Not set on a row that should go.** The mark is set only when the message is deleted for everyone at that moment (the `EXISTS` in `KEEP_DELETED`). Measured, a reaction or an edit on a message only deleted for you goes, with nothing said. But no test pins it (T1).
- **The withdrawal drops only a row still queued.** It never drops one the engine or a receipt has answered for, and never sends one twice: it drops a row only while it's queued, in the transaction that checks, and a chat runs one attempt at a time. A row that *may* have gone, handed to the engine when jawd stopped, is withdrawn at the next start and said not to have been sent, and a receipt for it then stores nothing (H35). That has been so since H22 for a message deleted for everyone, and now holds once it's deleted for you too.
- **Every order I could make.** My scenes are in Measurements. Every order deleted for everyone first behaves as the builder's tests do: withdrawn once, with one notice. That holds however the deletions came, asked again, replayed, or across a kill between the deletion for you and the withdrawal. Two orders behave otherwise (H33, H34).

### The outbox's bound and counters

- **Counted the same, marked or not.** `WAITING` (`store/write/outbox.rs:211`) counts rows whatever their mark. The withdrawal is `acted(went = false)`: it drops the row and writes no count. `jawd status` reads its counts by query (`state.rs:205`). The branch adds no queue or file.

The app state row took the 1,000th place, and a send was refused with error 5. A deletion for you of the reaction's message is refused with error 5, and the count stays (1,000, 1,000). With a failed row aimed at the message counted as freeing a place, the deletion is taken.

### H24

- **One place.** `message_row` (`store/read.rs:390`) builds every message row an interface is sent: windows, a single message (also `send.text`'s answer), and search hits (`search`, `messages_by_t`). The chat list's last message carries no reactions, and no notice or notification names one.
