## Findings

### Data loss and inconsistency: none

- **The kept JSON is the row a fresh query gives.**
  - `Line::of` (`client.rs:220-225`) writes the row with `serde_json::value::to_raw_value`, the same bytes `serde_json::to_vec` gives. It hashes those bytes and keeps them, with the id, sort and version from the same struct.
  - `push` writes the kept bytes as they are (`:509-538`), and `result` parses them into a watch's or move's answer.
  - Rows come from `window::query`'s one read transaction (`window.rs:81-153`), and `chat_row` and `message_row` read nothing else. There's no clock, and `typing`, `reactions` and `children_unread` are constants. `spans` and `detail` are parsed from their columns, and serde_json's maps are sorted, since `preserve_order` is off. So a fresh query of the same snapshot makes the same bytes.
  - A window takes a kept read only if the read has every change its connection has heard of (`client.rs:848`), so no change since the read has touched those rows.
  - A chat list held while catching up keeps its interface's order. Its sorts are put back before the JSON is made (`:1028-1037`), and that read stays the connection's own.
  - On the wire, a row's keys now come in its struct's order, where main's went through a `Value` and came sorted. JSON doesn't depend on key order, and jaw-client reads rows by name.
- **What letting a read go makes possible is covered.**
  - Once a slot's read is let go, `is_none_or` (`client.rs:878`) has nothing to compare the next read with, so whichever read finishes next is kept, however old. A slot can now keep a read older than one it let go.
  - A window still can't take it, since it never takes a read older than what its interface holds (`owed`, `:634-636`, T2's rule).
  - Without that rule, the probe at 8 KB finds exactly this: "w6 went back from seq 606 to 604".
- **The byte counter is exact.** `keep` adds a read's bytes (`client.rs:272-275`) and `Kept::drop` subtracts them (`:158-162`), however the read goes: replaced, let go, or with its slot. Every mutation of that accounting fails the bytes test (B1 to B3 and B6 in Measurements), and so does counting slots no window holds (S2).
- **Nothing depends on a kept read.** A window whose slot let its read go joins a read under way or asks for one (`client.rs:852-886`). The bytes test goes through that path, and the probe goes through it thousands of times in each run.

### Unpredictable performance (follow-ups; no budget broken)

- **P1 is closed, with three edges.**
  - The 16 MiB bound counts what reads ask of the allocator. malloc's rounding makes the heap 6 to 12% more, up to about 18 MiB. That's not a budget, so it may stand, but "counted exactly" means the request, not the heap.
  - Reads in flight aren't counted. At most one waits for each connection, since a flush awaits its windows in turn, plus one for each connection that left while its read ran. At its peak a read now holds its rows twice, as structs and as JSON, where main dropped each row's JSON once it had hashed it. For jaw's windows that's tens of kilobytes. By my estimate, 2,001 messages of 64 KB would take about 260 MB, twice main's peak, but such a window was already over jawd's budget on main.
  - The number of connections is still unbounded. Each holds its windows' hashes, at about 160 bytes a row, so about 10 MB at 32 windows of 2,001 rows. Its queue to its interface is bounded at 64 lines, not in bytes. Both are as on main, where windows weren't capped at all.
- **The bench.** With one interface the branch costs what main does: a lone message's p50 was 0.67 to 0.84 ms on both. With 4 interfaces, every interface's p99 was 1.37 and 2.30 ms quiet, and 1.44 and 1.54 ms busy. Main's was 4.48 and 6.23 ms quiet, and 4.71 and 5.54 ms busy. jawd used 49 to 64% of a core with interfaces watching, against main's 61 to 102%.

### Hygiene (follow-ups; none blocks)

- **H4. Which kept read goes first isn't pinned.** Letting the newest go first (`client.rs:294`, reversed) passes every test. Under pressure, that would let go the read other connections are about to take, so each of them reads again. A test with room for one of two kept reads, checking the newer one stays, would pin it.
- **H5. T1's test can hang instead of failing.** Its wait for the slow read to be asked for (`tests.rs:1850`) has no deadline. Under a mutation where no read was asked for (taking any kept read), it spun at full CPU for 8 minutes until I stopped it. A deadline would make it fail.
- **H6. `detail` keys could collide with a row's fields.** `MessageRow` flattens `detail` into the row. If a converter wrote a top-level detail key named like a row field (`kind`, `status`, `id`), the row's JSON would now carry that key twice: serde_json's `Value` would keep the last, and a typed parse of `MessageRow` would refuse it. Main's `to_value` kept the last without a word. No converter writes one today: detail's top-level keys are `system`, `link`, `media`, `location`, `contact`, `contacts`, `poll`, `event`, `invite`, `video` and `album`. A test over the converters' detail keys would keep it so.
- **H7.** The protocol README's table of errors says code 5 covers presence subscriptions and a file too large, but not windows. The Windows section does say it.

### On main, outside this branch: the reply that waits for room (`sock.rs:100`, `:105`)

The builder's diagnosis holds. A connection's loop awaits `out.send(reply)` inside its `select!` arm. While the queue to its interface is full, nothing polls the connection's windows, so `Ready::Behind` never fires and they're never dropped or resynced.

I showed it with a test in scratch copies of the branch and of main, with `behind` at 2 s. An interface watches the open chat and stops reading, while a message arrives every 12 ms:
- **With no request,** its window is dropped within 8 s, and once it reads again, a `resync` comes.
- **With one `status` request,** sent after jawd's queue to it has filled but before `behind` has passed, its window is still watched 8 s later, four times `behind`. Once it reads again, only the reply comes, and no `resync`.

What it costs:
- **Nothing is lost or wrong.** The reply waits; it isn't sent early or dropped. A later request waits in the socket, unanswered and so unacknowledged. Once the interface reads, its windows converge through the lag path that T3 pins.
- **It breaks the design's "one too far behind is told to watch again".** A connection that stays open without reading keeps its windows, their slots and kept reads, its hashes and its 64 queued lines for as long as it stays.
- **It can't hold another connection up.** Shared reads run on tasks of their own, and no lock is held across the wait.

**Should it be fixed before this lands? No.** It predates the branch, which changes neither `sock.rs` nor the `Behind` path, and doesn't make the stall likelier. The branch's cap of 32 windows and its shared byte bound limit what a stalled connection holds, where main limited neither. It should be the socket's next change, audited like this one, since `sock.rs` is among the data layer's paths. The fix:
- keep at most one reply waiting for room;
- stop reading requests while it waits, so the window cap and the resync list stay bounded;
- go on polling the windows meanwhile, so `Behind` can fire.

My test (`/tmp/jaw-r2-audit-tests.rs`, with its variant for main) can pin it. jaw-client's `an_interface_that_falls_behind_is_told_to_watch_again_and_ends_as_a_fresh_one` passed 4 of 4 here, at load 14 to 19. So I couldn't reproduce its flake, but this mechanism explains it. The builder's race in jaw's test harness is in jaw's tests, outside the data layer, and I didn't examine it.

# First audit: 5661bc7 (kept as written)

Range: c2c60f6..5661bc7 in feed-many (f3c10bc, 5661bc7), 2026-10-25. Auditor: database-expert.

What the branch does: connections watching an identical window (the same `Spec`: folder or chat, anchor with its cursor, before and after) share a `Slot` (`client.rs:84-106`). The slot holds the window's newest successful read (`Found`: its rows, each with its hash, the seq it's as of, and `fresh`, the seq it has every change up to) and the read under way (`Reading`, with `from`, the feed's committed seq when it was asked for). A flush takes the kept read if it has every change the connection has heard of. Failing that, it joins the read under way if that was asked for after them, or else asks for a new read on a task of its own, which others can join (`shared`, `client.rs:668-709`). Each connection then diffs the read against its own hashes. A chat list owed a reorder is paced by its reads (`reorder_at`, `:511-518`), and `keep` clears the failure timer (`:527`), so a successful `watch.move` starts it again. 5661bc7 changes what a window asks of a shared read, from every change that marked it to every change its connection has heard of (`owed`, `:472-474`; `heard`, `:781`). A lagged connection's windows ask for a read made after the lag (`wait(now, i64::MAX)`, `:767`). There's no SQL, schema, migration, PRAGMA, index or ack change. `window::query` is unchanged, and `read.rs` only derives `Hash` for the two cursors.

The step's goal, from the first feed audit's follow-ups: a lone message within 5 ms at p99 to the open chat's window with 4 interfaces (and 8), keeping every guarantee that audit approved.

## Findings

### Data loss and inconsistency: none in the code

I found no way for a shared read to give a connection a window other than a fresh query of that window's own spec. This is the argument I checked:

- The store publishes `committed` only after `tx.commit()` returns (`store/mod.rs:1257-1271`, and `:950-954` for live writes that share an inbox commit). The single writer gives seqs in commit order. So a read asked for after `from` was taken has a snapshot with every commit up to `from`, and `fresh = max(from, snapshot seq)` (`client.rs:175`) is a true lower bound. The `max` also covers an events table pruned empty, where `feed_bounds` gives 0.
- A connection hears the feed's batches in seq order without gaps, or is told it lagged. It judges each change against the rows it holds. Requiring `fresh ≥ heard` means every change it has judged is in the read it takes, and it judges every later change against that read's rows. That's the induction main relied on with reads of its own. `from ≥ owed` gives the same for a read not yet answered. `max(state.fresh)` keeps a window from taking a read older than the one it holds, and `i64::MAX` makes a lagged connection wait for a read asked for after whatever it lost.
- A slot's spec is its windows' spec. `slot()` is keyed by it, and a window moves to `slot(found.spec)` whenever a read moves its anchor's cursor (`:872-875`). So a window only ever takes reads of its own spec. A window whose push doesn't fit keeps its rows and stays marked, as on main.
- The chat list's read while catching up (`only`, `:836-851`) stays per connection and isn't kept in the slot, so one connection's rows kept in place never reach another.

The probe below (five racing connections through moves, re-watches, catch-up holds, failing reads, a slow connection, one stalled until it's resynced, and lags) found nothing in 86 seeds. Neither did the branch's own tests, six times.

### Three rules the change adds that no test pins (must change)

Each guards against an inconsistency, and each is implemented correctly: the probe passes with all three in place. But removing any one of them leaves all 16 feed tests passing. The brief requires a test that fails without each rule a change touches. Tests that do are in `/tmp/jaw-audit-feed-many-probes.diff`, which applies to 5661bc7.

- **T1. A read under way is joined only if it was asked for after every change the connection has heard of** (`client.rs:674`, `reading.from >= owed`). Suppose a connection hears a new message while it waits out its pace. Without the check, it joins a read asked for before that message. It keeps that read's rows and clears what it owed, so the open chat's window stays without the message until something else touches the chat. With the check removed, all 16 feed tests pass, and so do 12 seeds of the probe. Fix: adopt `audit_a_read_under_way_is_taken_only_if_it_was_asked_for_after_every_change_heard`. Without the check it fails 3 of 3: the window holds `o1 o2 o3` where a fresh query has `o4`. It needs a `cfg(test)` way to hold a read's answer back after its snapshot is taken (`Feed::slow_reads` in the diff) and a way to know the read was asked for. The diff uses a test-only counter; a count of reads asked for, kept in `Shared`, would do.
- **T2. A window never takes a read older than the one it holds** (`client.rs:473`, `.max(self.state.fresh)`). A connection's own last read can be newer than what it has heard. That happens after `watch`, `watch.move`, a resync's watch or a chat list's read while catching up, all of which read for that connection alone, and after taking a kept read newer than its `heard`. When it then hears a change the slot's older read has, it would take that read. The window goes back, and a push as of an older seq removes rows the interface held, until the next change puts them back. Removing the rule leaves all 16 feed tests passing. Fix: adopt `audit_a_window_never_takes_a_read_older_than_what_its_interface_holds`, which fails 3 of 3 without the rule ("a push as of seq 5 after a move as of 7"). Also check in the racing multi-connection test that no window's seq ever goes back; that's how the probe found it (seed 6, the slow connection's top chat list: "w1 went back from seq 664 to 621").
- **T3. A lagged connection takes only a read asked for after the lag** (`client.rs:767`). With `wait(now, 0)` instead, a lagged connection takes the kept read, which can predate the changes it lost and will never hear. Its window stays stale. No feed test lags a connection, and all 16 pass with the mutation. Fix: adopt `audit_a_lagged_connection_takes_only_a_read_asked_for_after_the_lag`, which uses a `cfg(test)` `Feed::start_keeping` to keep 4 batches. Without the rule it fails 3 of 3: the window holds `o1 o2` where a fresh query has `o3`.

### Unpredictable performance (follow-ups; no budget broken as jaw uses windows today)

- **P1. Kept rows are bounded only by the windows watched, and nothing bounds those.** Each distinct window keeps its last read's rows for as long as anyone watches it, idle or not. Measured with a counting allocator, for short text messages and chats, a kept read is:
  - 125 KB for 100 messages, and 1.2 MB for 1,000, so about 2.4 MB at the cap of 2,001 rows;
  - 52 KB for 100 chats, and 503 KB for 1,000.

  Main kept only a connection's hashes for the same windows: 11 KB, 160 KB, 14 KB and 184 KB. jaw's own windows (100 chats, and 100 or 201 messages) keep about 0.2 to 0.4 MB, shared by every interface, which is fine. But an interface or script watching 40 distinct windows at the cap would hold about 100 MB, jawd's whole steady budget, where main held about 13 MB. Rows with long text, link previews or polls cost more. Fix: size the kept reads in bytes, as principle 5 asks of caches. A slot can drop its kept read under pressure, since correctness doesn't depend on it: a window without one asks for a read, and `state.fresh` keeps it from going back. Also cap windows per connection, and report windows and kept bytes in `jawd status`.
- **P2. Tails under load with 8 interfaces.** I made six runs with 8 interfaces at loads of 18 to 34. In three of the branch's four, the busy p99 was 13.2, 13.5 and 25.2 ms, and its fourth had a quiet-phase tail on the first interface instead (7.3 ms). Main's busy p99 was 25.3 and 29.4 ms in both of its two. Each tail hit all eight interfaces together, with their p99s within 0.2 ms of each other, so a handful of messages were late for everyone. The tails came and went between identical runs, and were gone at loads of 10 to 14. There every interface's p99 was 2.0 to 2.6 ms quiet and 1.9 ms busy, and the slowest of 2,400 deliveries took 3.8 ms. I take them to be the machine. But as the first audit asked, the run on a quiet machine (load under 2; 1, 2, 4 and 8 interfaces, three runs each) is still owed before the goal for 8 interfaces can be called met. The goal for 4 is met by a wide margin (see Measurements).

### Hygiene

- **H1.** If a shared read's task panicked after its read (`client.rs:684-698`), `state.reading` would stay set. Windows whose `owed` it covers would join it and fail until `behind`, then resync. Nothing in that task can panic today, since the read pool turns a reader's panic into an error (`store/read.rs:80`). Clearing `reading` with a drop guard would only be hardening.
- **H2.** The bench times only the first interface, and with shared reads the other interfaces matter as much. Report each interface's p99 and the worst. On main the others were worse than the first: with 4 interfaces, the first's p99 was 5.6 ms and the worst one's 6.6 ms. The patch used here is `/tmp/jaw-audit-bench-all-interfaces.diff`.
- **H3.** While catching up, chat lists still read once per connection (`only`), as on main, so N interfaces cost N reads every burst. This is a follow-up if latency while catching up with several interfaces matters.

### What holds

- **The first feed audit's follow-ups.** A reorder is paced by its reads, and a successful move restarts the failure timer; each has a new test that fails without it (mutations M5 and M6 below). Identical windows share their reads: without sharing, the new test counts 10 reads instead of 3. Conversations still go before chat lists within a connection.
- **A slow, stalled, failing or departed connection can't affect another's window.**
  - The slot's lock is never held across an await. `shared` drops it before waiting, and the read's task takes it only briefly.
  - A read runs on its own task, so one asked for by a connection that goes still runs to its end for the others.
  - A read's error goes to everyone waiting on it, and the slot forgets the reading. The next flush asks again, at each window's own pace and with each window's own failure timer.
  - A connection with a full queue asks for no read, since `flush` checks for room first (`:826-829`).
  - Hashes, pacing and timers stay per connection.

  In the probe, the slow connection, the stalled one (2,466 resyncs) and the spells of failing reads never left another connection's window wrong.
- **No snapshot pins the WAL.** A kept read is plain memory. Each read is one transaction, ended before it answers, as on main, and there are fewer of them (reads a second below).
- **Pacing.** No window got more than 20 batches in any second, in every run on either build.
- **Reconnects.** jaw keeps each window's own seq and sends it as that window's `since` (`jaw-client/src/client.rs:672`, `:992`), and chat lists are watched again whole. So shared reads leaving one connection's windows at different seqs can't make a reconnect skip a row.

## Verdict

Nothing marked data loss or inconsistency is in the code. Sharing holds every guarantee the first feed audit approved: windows equal a fresh query of their own spec, at most 20 batches a second per window, a slow client holds nobody up, and no snapshot pins the WAL. The goal for 4 interfaces is met with a wide margin: every interface's p99 was 1.6 to 1.9 ms quiet and 1.9 to 2.1 ms busy, against main's 5.2 to 6.5 ms and 7.4 to 16.7 ms. But three rules the change adds have no test that fails without them, and that must change before it lands:

- T1: a read under way is joined only if it was asked for after every change heard.
- T2: a window never takes a read older than the one it holds.
- T3: a lagged connection takes only a read asked for after the lag.

Tests for all three are in `/tmp/jaw-audit-feed-many-probes.diff`. It would also be worth adopting the probe, or adding to the racing multi-connection test moves, re-watches, holds, failing spells, a slow connection and the check that no window's seq goes back. Follow-ups that may stand once the tests are in: P1, sizing kept reads in bytes, capping windows per connection and reporting both in `jawd status`; P2, the quiet-machine run for 8 interfaces; and H1 to H3.

Verdict: changes needed
