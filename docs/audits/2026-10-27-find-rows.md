# Audit: find answers with the rows the windows send

Range: `1e6c580..19bee7b` in `find-rows` (one commit, `19bee7b`), 27 October 2026. Auditor: database-expert. Line numbers are at `19bee7b`.

The machine (Mac Studio, M1 Ultra, 20 cores, 128 GB, macOS 26.6.2) was busy with other agents throughout: one-minute load averages of 52 to 78. Every timing says the load it was taken at.

## Summary

The fix is sound, and it does what the protocol always said.
- find now builds each chat hit's row with `feed::chat_row` and each message hit's row with `feed::message_row` (`find/mod.rs:248`, `:217`): the functions the windows, `chat.start` and `send.text` already use (`feed/window.rs:156-220`, `send/start.rs:52`, `send/outbox.rs:174`). A found chat or message is now exactly the row its window sends.
- Nothing else in the data layer changed: no SQL, statement, plan, transaction, ack, migration, schema or PRAGMA, and nothing in `store/`, `sync/`, the engine or `proto/`. find still writes nothing, and reads on the read pool with the same three statements (`read::matching`, `read::messages_by_t`, `read::chat`), so `plans.txt` stands.
- Cost: no measurable change end to end on a million messages. The conversion itself adds 0.08 ms for 200 plain hits and 1.3 ms for 200 heavy ones, in release. The search budget holds.
- Tests: the new socket test fails with either conversion reverted, and it's the only test that does.

Findings:
- No data loss, no inconsistency, and nothing that breaks a budget.
- Two hygiene items stand as follow-ups: P1, the conversion runs under the name index's lock on a tokio worker; H1, the fixture test can't see a jaw.db field leaked into a message row.

The commit touches `crates/jawd/src/find` and `crates/jawd/src/feed/` (`scripts/check-data-audit.py:18-19`), so it carries the trailer `Data-Audit: docs/audits/2026-10-27-find-rows.md`.

## The questions asked

### Is every found row now what its window sends?

Yes, every row, not only the test's.
- Both sides read the same columns through the same store function. find's `read::messages_by_t` and the windows' `read::messages` both select `MESSAGE_COLUMNS` with `MESSAGE_JOINS` into `read::message_row`, the outbox overlay included (`store/read.rs:446-470`, `:579-590`). find's `read::chat` and the windows' `read::chats` both select `CHAT_COLUMNS` into `read::chat_row` (`:304-320`). The wire conversion is now the same function as well. So the test's one chat and one plain message stand for quotes, details, reactions and pending effects too.
- `v` is the same. Under the README's "a `row` in a reply is an upsert like any other, applied by its `v`", an interface that applied a found row used to get, at the window's `v`, a row without `sort`. Now it gets the window's row.
- They can differ in one place: a chat list held while catching up. A window row keeps the `sort` it had at the last reorder (`feed/client.rs:1072-1078`), while a found chat has its place now, as `chat.start`'s row already does. Neither interface puts a found chat into its chat list: the terminal opens it, or keeps it as the chat outside the list (`view/palette.rs:1036-1044`), and the Mac's palette lists it. So nothing changes.
- `typing` and `children_unread` are fixed in `chat_row`. When typing leaves chat rows (protocol 2, decided in `1e6c580`), found chats follow without find changing, and the fixture test makes find's fixture change with them.

### Did anything rely on the old shape?

No. I searched jawd, jaw, jaw-client, jaw-proto and `scripts/` for reads of a hit's row.
- jawd's tests read `row["id"]`, and a person's `row["phone"]` (`find/mod.rs:446`, `:468`, `:513`, `sock.rs:1107`), which both shapes have. The demo's probe reads only `counts.message` (`demo/probe.rs:191`), and `find/bench.rs` only kinds and texts.
- jaw-client passes `row` on as JSON. The terminal reads a chat hit as its `Chat` and a message hit as its `Message` (`data.rs:756-759`). Neither has `n`, `person`, `summary` or a nested `detail`, and both need `sort`, so its palette dropped every message hit, silently, through `wire.rs:528`'s `filter_map(… .ok())`.
- The Mac's `Hit` decodes a row with its window types and falls back to `.other` (the builder's copy, `swift/Find.swift`). I ran the builder's compiled decoder again: jawd's old answer leaves the message as `.other` (`keyNotFound 'sort'`), and the new one lists it.
- The fields that go (`n`, `person`, `summary`, the nested `detail`) were never in the protocol, so its version needn't change.

### Can a row make find fail, or fail differently?

- No new failure. `message_row` turns spans, a quote or a detail it can't parse into null or nothing, and reactions into none (`feed/window.rs:190-194`, `:211`). The store's reader already refuses a column that isn't JSON before either side runs. Whatever row the windows can show, find can show.
- Very large rows: a 64 KB message converts in 0.017 ms (release).
- Memory: still at most 200 message hits. For plain messages the reply is about 11% smaller, since `summary` and `n` go: 106,539 against 119,292 bytes for 200 hits.

### Durability, schema, migrations, plans and the edge cases

- Nothing is acknowledged: find is a read. `chat.opened`'s durable write is unchanged.
- No table, column, `CHECK`, trigger, index or migration changed, and no statement or plan.
- Disk full, two processes, clock changes and unclean shutdowns don't reach a serialization of rows already read. The change adds no commit.

## Findings

### P1. A find's message rows are converted on a tokio worker, under the name index's read lock (hygiene, a follow-up)

- **Where:** `find/mod.rs:208-219`. The loop that makes message hits holds `self.inner.index.read()` for all of its rows, while only `chat_name_of` needs it. Meanwhile `feed::message_row` parses each row's spans, quote, detail and reactions, and `to_value` copies them into the hit. The index's refresh takes the write lock on a tokio worker (`:131`), so the refresh, and that worker, wait for the loop to end.
- **What changed:** this was so before, but the loop now costs more. For 200 heavy hits (1 KB of text, 19 spans, a quote, a poll or a link, and six reactions each), it holds the lock for 3.0 ms instead of 1.7 ms in release (p50; 4.2 against 3.3 ms at p99). In a debug build, which is what the owner's jawd is today, it holds it for 16.1 ms instead of 3.4 ms. For 10 heavy hits it's 0.17 against 0.10 ms in release.
- **Why it can stand:** no budget breaks. The 50 ms search budget is for a keystroke's find (10 hits of each kind), and 200 hits come only when an interface asks for them. With the bench's plain messages the difference is under 0.1 ms.
- **Fix:** convert the rows where they're read, in the reader's closure (`:177-187`), and take the lock only to look up the chat names. Or at least convert them before taking it.

### H1. The fixture test can't see a jaw.db field leaked into a message row (hygiene, a follow-up)

- **Where:** `jaw-proto/tests/fixtures.rs:108-109`, with `windows.rs:225`. `MessageRow` flattens its `detail`, so a key it doesn't name is kept as a detail and written back the same.
- **Measured:** find's fixture with the store's message row (a bare number for `from.id`, no `sort`) fails, and so does one with `n` and `person` added to the chat row. But one with `n`, `summary` and `"detail": null` added to the window's message row passes.
- **What's covered:** jawd's side. The socket test compares the whole row with the window's, so a field leaking from jawd fails it. What isn't covered is a fixture edited by hand.
- **Fix:** in the fixture test, check that a message row's detail keys are among the kinds `windows.rs:223-224` names (`media`, `voice`, `link`, `poll`, `location`, `contact`, `event`, `system`).

## Tests

The rule the change touches is the protocol's: "`row` is what was found: a chat as `chats.watch` sends it, a message as `messages.watch` does." The new test, `a_chat_and_a_message_find_finds_come_as_their_windows_send_them` (`feed/tests.rs:2809`), checks it over a real socket. Its finder starts after the test's writes are committed and indexed, and loads its names from jaw.db, so the test doesn't race.

Mutants were built in my clone (debug) and run against the find, socket and feed-find tests, 41 in all:

| Mutant | Result |
| --- | --- |
| Only the chat conversion reverted, `to_value(&chat)` (`:248`) | the new test fails at its chat assertion (`feed/tests.rs:2834`); the other 40 pass |
| Only the message conversion reverted, `to_value(&row)` (`:217`) | the new test fails at its message assertion (`:2836`); the other 40 pass |
| Both reverted | the builder's red run: fails at the chat assertion, with jawd's real answer in the message |

Fixture mutants, through `jaw-proto`'s fixture test:
- The store's message row: fails ("invalid type: integer `12`, expected a string").
- The chat row with `n` and `person`: fails ("doesn't write back the same").
- The message row with `n`, `summary` and `detail`: passes (H1).

At `19bee7b`, at loads of 52 to 69:
- The new test passed 8 of 8 runs.
- The find, socket and feed-find tests passed, 41 of 41, and so did the feed and send suites, 110 of 110 (2 ignored, as on main). `jaw-proto`'s fixture test and the terminal's `data::` tests passed.
- `cargo fmt --check` passed.
- The terminal's `wire::` tests passed 32 of 33. The failure was `the_first_frame_with_a_conversation_is_drawn_as_soon_as_jawds_answers_come`, a timing bound of two frames: 139 ms at a load of 59, and 72 ms in 1 of 3 runs alone at 64. This branch changes only a test's expected value in `jaw` (`data.rs:1089`, in `mod tests`), so that code is main's.
- The builder's gate passed fmt, clippy, gofmt, go vet and `go test -race`. Its four store timing tests and the keypress bench failed at loads around 70, on main's binaries as on the branch's (its `gate/flakes.txt`), in code this branch doesn't touch.
