## Main's two checkpointer flush tests, and P8

**Judgement: acceptable for this branch; the fix belongs in the tests, which are main's.** The branch changes nothing in how the writer outruns a pass or how the checkpointer flushes after one. It makes each burst the tests write somewhat dearer, and the suite they run in heavier. The tests are `the_checkpointer_flushes_jaw_db_after_a_pass_the_writer_outran_and_not_after_one_that_reached_the_end` and `the_checkpointer_flushes_jaw_db_without_letting_go_of_this_processs_locks_on_it`. (The previous round-three auditor ran a third, the reader's, in place of the second.)

- **The mechanism is the same on both builds.** My probe `audit_time_to_first_flush` runs `outrunning_a_pass`'s loop and records each burst. I ran it six copies at a time, main's build and the trial's in turn, four rounds, at a load of 65 to 67. In 48 of 48 runs the first flush came after the third burst. The WAL's frames suggest why: a burst writes about 700, under `WAL_EASY` (1,024), so the first pass starts after the second burst, a live write lands in it, and the loop sees the flush once the third returns.

  - A burst took 140 to 345 ms on main and 151 to 386 ms on the trial, about 8% more at the median.

- **Alone, run in turn,** at a load of 62 to 66: 20 of 20 passed, main's in 1.8 to 4.3 s and the trial's in 2.2 to 5.7 s.
- **In a whole jawd suite** (the unit tests, 639 of main's and 680 of the trial's, each test's time from `--report-time`), every run passed both tests:

  | --- | --- | --- | --- |

#[tokio::test(flavor = "multi_thread")]
async fn audit_the_trees_pushes_carry_the_favourite_slots_when_they_change_and_only_then() {
    async fn pushes(watcher: &mut Watcher, seq: i64) -> Vec<Value> {
        let mut out = Vec::new();
        loop {
            while let Ok(line) = watcher.lines.try_recv() {
                let FromJawd::Push(push) = serde_json::from_slice(&line).unwrap() else { panic!("a reply") };
                out.push(json!({"method": push.method, "params": push.params}));
            }
            if watcher.seen >= seq && !watcher.client.pending() {
                return out;
            }
            watcher.turn().await;
        }
    }

    let seq = bed.apply(vec![Change::Message(text(ANA, "a1", AT, Some(ANA), "olá"))]).await;
    let mut watcher = bed.watcher(64);

    };

### Unpredictable performance (follow-ups; none breaks a budget in steady use)

- **P1. Moving or deleting a big folder holds the writer.**
  - The transaction body is 15.9 ms to move a folder of 1,000 items under six folders, and 23.0 ms to delete it, against 0.6 ms for 20 items (release build, the writer's settings, load 78 to 85).
  - An incoming message's ack waits behind it. The cost grows with items times depth, since each path changed touches every item under it.
  - Say so in the design, or bound it.
- **P2. The mend holds the writer 8.1 ms** (6.9 to 10.1) in one background transaction, against the 3 ms budget. It runs only when drift is found, which should be never.
- **P3. Presence writes can be one long transaction.**
  - `write_heard` takes up to 1,024 heard events into one live apply (`presence.rs:195`), which is 4.9 ms. Following 200 people takes 0.29 ms, and clearing presence on a new connection 1.1 ms.
  - A cap near 100 a transaction would keep presence under a millisecond.
- **P4. Smart folders without `unread` or `mentions` walk every unarchived chat.**
  - "Waiting on me" is read on `chats_by_sort` and checked row by row (`store/lists.rs:152`, `:172`), for each page and each count. "Stopping at a thousand" stops at a thousand matches, not rows read.
  - The tree's window counts every smart folder on each read, and the flood read it 16 to 17 times a second.
  - Measured: the tree read in 1.3 to 1.7 ms with three smart folders on 3,000 chats (load 65 to 74), and Waiting on me watched in 5.2 and 14.0 ms (p50), 13.3 and 30.8 ms (p99), at load 47 to 64.
  - An index for it, or a count kept, when accounts grow.
- **P5. Rosters are counted and read again more than they need.**
  - `roster_count` for unread, archived and smart lists pages `people_roster` until it has a thousand (`store/lists.rs:848`), so a selective list walks every person in the roster. All counts the whole roster at each read.
  - Every roster window is read again on every chat change. In the flood the two rosters got 0.3 to 0.5 pushes a second, while every watched window was read up to 17 times a second.
  - jawd's CPU went from 57 to 74% of a core to 103 to 116% with seven windows watched, the builder's flag.
  - Mark rosters only for people and their one-to-one chats, as messages windows track senders.
- **P6. The about-texts query walks its whole index when nobody is due.**
  - `about_at IS NULL OR about_at < ?` can't seek, so the query walks `people_about_due` to its end every minute (`presence.rs:380`).
  - Two seeks, the NULLs and then the range, would stop at once.
- **P7. Preparing the hottest chat updates costs about nine times more.**
  - The chat update for a new message now takes 52 µs to prepare (p50), and settle's 46 µs, against 6 and 4 µs at version 11, since six chat triggers compile into them.
  - The writer caches 64 statements (`store/mod.rs:332`), and this branch adds about forty to its set, so each eviction pays that again. The data review's H2 (128) would cover it.
