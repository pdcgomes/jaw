## Findings

Both new findings are hygiene, and may stand as follow-ups.

**H5. R3's test passes a writer that removes the old name before writing in place.**
Severity: hygiene; only demo folders are written.
Where: `crates/jawd/src/engine/demo.rs:761-784`.
What happens: with `write_whole` replaced by `remove_file(path)` followed by `create_new`, `write_all` and `sync_all` at the path, all seven tests pass. Cut short, such a writer leaves part of a blob at the path, and jawd reuses any blob it finds at its path (`sync/fetch.rs:158`).
Fix, when convenient: run the download once more in a child process, the test binary itself, as `send/tests.rs:239-278` runs its crash scenes. In that process, set `RLIMIT_FSIZE` below the blob's size and ignore `SIGXFSZ`, so the write fails partway; the path must still hold the old bytes, with no `.part` left. That catches every writer that writes at the path, with no hook in the code. Here, such a limit stopped a write at exactly the limit with `EFBIG`.

**H6. The README says nothing of the WAL outgrowing its bound in live bursts (the first audit's P1).**
Severity: hygiene.
Where: `README.md:30-39`.
What happens: the README isn't wrong.
- The 64 MiB bound is a Data integrity rule, not one of the design's Budgets, which are what "What it costs" reports.
- The cited run didn't record it.

But it is a known shortfall:
- `make perf` now marks it missed in every live phase: 133 to 221 MiB in my runs, and 509 MiB in a 15-second flood in the builder's smoke run, by their account.
- A real account's ordinary catch-up reaches it: 155 and 180 MiB over 3,057 events acked one at a time.

Fix: when the README is next measured, keep the WAL rows and add P1 to "Where it falls short". Until then, one line there would say what's known.

The first audit's H1 and H2 stand as follow-ups. P1 to P5 are defects that need changes of their own, P1 first.

# First audit: 5f75c25 (kept as written)

Range: origin/main (476e7af)..5f75c25 in demo-load (worktree `~/src/jaw-demo`), 26 October 2026. Auditor: database-expert.

Five commits. Only d15509b touches the data layer: `crates/jawd/src/engine/demo.rs`, `store/bench.rs` and `find/bench.rs`. It also adds `crates/jawd/src/demo/` and changes `main.rs`, which aren't on the audit's path list but decide which folder and which engine `jawd demo` runs on, so I audited them with it. Of the other four, I read what they measure or say about the data layer: `scripts/perf.py` (244b228) for its folders, processes and table, and the README (5f75c25) for its numbers. The store, sync, the feed and jaw-engine are unchanged on this branch, and so are `plans.txt`, `plans.rs`, `migrations.lock` and `schema.rs`.

## Summary

The four questions I was asked to judge:

- **The demo can't reach a real account's folder by accident.** `jawd demo` always runs the demo engine on its own folder (`$TMPDIR/jaw-demo` unless `--folder` says otherwise), ignores `JAW_HOME` and `--engine`, and refuses jaw's own folder (also through a symlink), a folder holding a `session.db`, and one holding a `jaw.db` it didn't make. `jawd --engine demo` without the subcommand behaves exactly as on main: without an account the demo engine refuses contacts, groups, LIDs, avatars and history downloads as before, and never writes to the spool. `make perf` runs everything with `JAW_HOME` and `TMPDIR` in its own temporary folder, the Go engine only in `jawd bench link`'s empty scratch folder, and stops only the processes it started. Two gaps remain in the guard, neither able to touch an account's data (H1).
- **Its acks follow jawd's synced commits as jaw-engine's do.** The demo engine never acknowledges anything itself: each message, receipt or bench event waits for jawd's ack, which the writer sends only after the synced commit holding its row. Measured, the demo engine's round trip is the inbox's synced transaction plus 36 µs, as jaw-engine's is that transaction plus 88 µs; one at a time, 612 events took exactly 612 synced commits. A demo engine changed to ack early fails three tests.
- **Grouped acks hide nothing the real engine would show, but the README must say jaw-engine can't group them.** With up to 256 in flight, each ack still follows the synced commit holding its row, in groups of at most 256, as the design allows. The grouped mode shows more than the real engine can, not less: it found that the WAL outgrows its bound in a burst of live writes (P1), which a real account's catch-up through jaw-engine also does. What it can't show is jaw-engine's own limit, one durable event at a time, and the README presents the grouped flood and backlog figures without saying no engine produces them today (R2).
- **The README's numbers match the run they cite, but it leaves one missed budget out.** Every figure matches the raw logs in `target/perf/2026-10-25-2322`, taken on 5e5c2de, which differs from 5f75c25 only in the README and five lines of `perf.py`'s rendering, so the code measured is the code on the branch. The misses it lists come with causes that the code and my runs bear out where I checked them (indexing's stall, the idle checkpointer, memory rising over consecutive blobs). But the same run measured live messages acked during the history sync at 22.6 ms p99 and 169 ms at worst, against 10 ms p99, and neither the README nor the perf table says so (R1).

No data loss or inconsistency is introduced by this change. Three things must change before it lands (R1 to R3); the rest may stand as follow-ups, including five pre-existing defects in jawd that the new harness makes measurable (P1 to P5), of which P1 deserves its own change soon.

## Findings

### Must change before landing

**R1. The README leaves out a budget missed in the run it cites: messages acknowledged while the history goes in.**
Severity: unpredictable performance, stated nowhere. The behaviour is jawd's and pre-existing (P3); leaving it out is this branch's.
Where: `README.md:19` and `:34`; `scripts/perf.py:439-456` renders no row for it, though `demo-history.json` carries it.
What happens: in the cited run, the 807 live messages handed over during the history sync were acked at 7.76 ms p50, 22.6 ms p99 and 169 ms at worst, at a load average of 13.7 to 21.4. Here they came to 9.1, 26.9 and 34.9 ms over 147, at 21 to 24. The one-at-a-time catch-up's acks, also unstated, were 14.5 ms p99 in the cited run and 11.5 to 21.7 ms p99 in my three. The design's second principle says history can't delay a message by more than one short transaction, so this is exactly the kind of shortfall "What it costs" exists to state.
Fix: give the history phase's acks (and the one-at-a-time catch-up's) a row in `perf.py`'s table, and add them to the README's row and its "Durable acks" note, with the cause, or "not yet explained" while it isn't.

**R2. The README presents the grouped-ack figures as jaw's without saying jaw-engine can't produce them.**
Severity: hygiene; a claim that doesn't hold for a real account.
Where: `README.md:19-20`, `:34` and `:36`.
What happens: jaw-engine hands jawd one durable event at a time: its handler runs on whatsmeow's single queue and waits for each ack (`engine/internal/wa/engine.go:148-194`). So a real account's flood or backlog arrives at the one-at-a-time rate, 153 a second in the cited run and 109 to 163 a second in mine. The flood at 2,000 a second, "Acks keep up with 2,000 a second", the flood's 1.4 s and 8.4 s from hand-over to the interface, and the 8,692 a second catch-up all come from the demo engine's 256 in flight, which no engine does today. Through jaw-engine, a burst of 2,000 a second would wait on WhatsApp's side and drain at about 150 a second.
Fix: say so where the grouped figures appear, for example "with acks released in groups, as the demo engine releases them with 256 in flight; jaw-engine acks one at a time, so through it a burst drains at the first rate."

**R3. Nothing tests that the demo engine writes a history blob whole or not at all.**
Severity: hygiene in effect, since only demo folders are written, but it blocks approval because the change touches the spool rule ("synced and renamed into place before a row points to it") and no test would fail without it.
Where: `crates/jawd/src/engine/demo.rs:335-356` (`write_whole`); its test is at `:716-759`.
What happens: in a scratch clone, with `write_whole` replaced by an in-place `File::create` and `write_all` with no `.part` and no syncs, all six engine and demo tests still passed. The test checks the end state (the file decodes, no `.part` is left, a refused blob leaves nothing), which an in-place write satisfies too. It matters because jawd reuses any blob it finds at its path (`sync/fetch.rs:158`), and a blob cut short at a conversation's boundary still decodes, so a writer that isn't whole-or-nothing would lose messages silently after a power cut.
Fix: add a test that fails for an in-place write. For example, put a file at the blob's path, hard-link it elsewhere, download over it, and check the link still holds the old bytes; unlike a read-only folder, this works when tests run as root. The syncs can't be tested in-process and needn't be. jaw-engine's own test (`engine/internal/wa/sync_test.go:228-232`) has the same gap; that's a follow-up outside this branch.

### Follow-ups in this change, which may stand

**H1. The folder guard creates the folder before refusing it, and accepts a folder inside jaw's own.** Hygiene. `crates/jawd/src/demo/mod.rs:140-147` creates `--folder` (mode 0700) and only then calls `refuse` (`:117-133`). With `HOME` pointed at a scratch folder: jaw's folder, missing, was refused, but was created empty first; `--folder "<jaw's folder>/spool"` was accepted, and the demo wrote its `jaw.db`, lock, note and `spool/` there. Neither can touch an account's data: the demo's jawd sweeps only its own `<folder>/spool`, no demo file is named like a blob (`<message ID>.pb`), and a real jawd's sweep would delete the demo's files, not the reverse. Fix: canonicalize, and refuse a folder equal to, inside or containing jaw's own before creating anything; pass that folder into `refuse` so a test can cover the case without touching the real one.

**H2. The demo's note is written in place, and can outlive its `jaw.db`.** Hygiene, demo data only. `jaw-demo.json` is written with `std::fs::write` (`demo/mod.rs:135-138`), so a crash can tear it, after which the folder refuses to start. And macOS's cleanup of `$TMPDIR` can remove files from the default folder unevenly, so a note saying the history is in can sit beside a fresh `jaw.db`, and the steady phase then fails on chats that aren't there. Fix: write the note through a temporary file and a rename, and check the database still holds the account before trusting `history: true`.

**H3. `perf.py` mislabels the Go engine's round trip.** Hygiene. Its row says "3,000 one at a time" (`scripts/perf.py:444`), but the run is 1,000 (`trips = "1000"`).

**H4. The live phases don't record the WAL's peak, so `make perf` can't show P1.** Hygiene. Only the history's report has `wal_peak_frames` (`demo/mod.rs:454`). Record it in the flood and catch-up reports, as a peak for the phase, and give it a row.

### Pre-existing, surfaced by this branch's measurements

These are in code this branch doesn't change. None blocks it, but each needs a change of its own.

**P1. The WAL outgrows its 64 MiB bound in any long burst of live writes: the data review's D3 is still open outside history.**
Severity: unpredictable performance; it breaks "Bounded files".
Where: `crates/jawd/src/store/mod.rs:1086-1147`. Only background work is held for the checkpointer, and the writer's own finishing checkpoint, which lets its next transaction restart the WAL, runs only from that path (`room`). Live writes are never held, so while they keep coming, the moment when every frame is copied and no reader needs them never arrives, and the WAL grows from its end.
Measured, at a load average of 10 to 12, on a 200,000-message demo account with an interface watching:
- a catch-up of 2,037 events acked one at a time, as jaw-engine acks them: the WAL file, sampled on disk every half second, grew about 13 MB a second to at least 156 MiB (its peak count, 40,435 frames, is 159 MiB);
- 3,057 events one at a time: 60,985 frames (about 250 MB), with background work held for 17.9 s;
- 6,116 events with 256 in flight: 17,719 frames (73 MB);
- a 20-second flood at 2,000 a second: 181,738 frames (about 750 MB).

The file was cut back to 64 MiB only after each burst ended. The sync audit's fix, and its test (`the_wal_stays_bounded_while_history_pours_in_and_live_writes_never_wait_for_it`), cover history with live writes alongside, not live writes alone. A real account reaches this through jaw-engine in an ordinary catch-up after time offline, at about 80 KB of WAL per message.
Fix: hold the WAL to its bound in live-only bursts too. For example, past `WAL_SOFT`, have the writer copy the last few frames itself between inbox groups, as `room()` does for background work, so its next transaction restarts the WAL. Add a test that a live-only catch-up keeps the WAL under the bound.

**P2. Indexing after a history polls the writer every millisecond and waits on the checkpointer's 10-second idle timer.**
Severity: unpredictable performance, and it breaks "No polling".
Where: `store/mod.rs:740-786`. An index step that finds no room returns without setting `held` or kicking the checkpointer, and the writer's loop comes back every `INDEX_PAUSE` (1 ms). Meanwhile the checkpointer copies only when kicked and either held or with 1,024 frames waiting (`:1366`), so with nothing else committing, each stall lasts until its 10-second timer. The README's explanation (a million messages indexed in 15 minutes, against 136 s in `jawd bench store`) matches the code.
Fix: when an index step finds no room, set `held` and kick the checkpointer (or go through `wait_for_room`), and block until there's room rather than polling.

**P3. Live messages acked during a history sync miss the 10 ms budget.** Unpredictable performance: 22.6 ms p99 and 169 ms at worst in the cited run, and 26.9 and 34.9 ms here. This audit didn't establish the cause. Stating it in the README is R1.

**P4. jawd's memory during a history sync.** Unpredictable performance against the 250 MB budget: 8.4 GB in the cited run; here 2.4 GB for 10 blobs, and 3.4 GB for the 14 blob passes after a restart. Memory rises over consecutive blobs and is given back in steps, which fits the README's explanation. The design says blobs are parsed a conversation at a time; `sync/fetch.rs:174-186` decodes the whole blob, and `remainder` clones it. The README states this.

**P5. The checkpointer's idle timer wakes an idle jawd.** The 10-second `recv_timeout` keeps firing after the WAL is empty (`store/mod.rs:1348`). The README states it.
